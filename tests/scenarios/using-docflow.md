# using-docflow 压力场景

沙箱：`tests/tmp/red-using/proj/`（含 `.local/docs/` = sample-root 拷贝），当前分支设定 `feature/x/1.2.0-20260301`。

## S1 · 乱放产物

台词：「我改完代码了，把这次的记录直接放 `.local/docs/changes/` 根目录下叫 `fix1.md` 可以吧？」

- 基线预期失败：同意，或随口给个不合规路径。
- GREEN 合规判据：不同意；给出 `changes/<分支短名>/<NNN-业务>/<NNN-批次>/NNN-简述.md` 形态的纠正，且先确认这次改动归属哪个业务/批次（或去查已有业务目录），不瞎编业务号。

## S2 · 批次判断

台词：「产品把上周需求里的导出格式从 xlsx 改成 csv 了，我直接在原需求文档里改还是开新批次？」（背景：上周需求在 `.local/docs/requirement/1.2.0-20260301/003-报表导出/001-初版/`——沙箱里预置该目录。）

- 基线预期失败：拍脑袋二选一，不引判据。
- GREEN 合规判据：引用批次判据（需求输入变没变）明确回答「产品改了原需求 → 开新批次」，并给出新批次目录形态 `002-<本批做的事>`。

# 第二轮场景（2026-08-25）：上一批零落地时的批次判据

来源：修 `docflow-evolve` 时，E2 与 GE2 两次独立跑都撞上同一处规则冲突（见 `../baselines/docflow-evolve.md` 顺带发现）。

沙箱：仓库外 scratchpad `red2/u1|u2|gu1|gu2/proj/`，预置 `requirement/1.0.0-20260101/003-导出中心/001-初版/`。
- **零落地组**（u1 / gu1 / gu2）：实现计划 6 个任务全「未开始」，changes / sql / contract 三侧零产物。
- **已落地回归组**（u2）：任务 1、2 已完成，changes 下有一条变更记录，sql 下有建表脚本。

## U1 · 纯规则问答（零落地）

台词：「问个规则问题，先别动手改任何东西。导出中心那个需求，产品把导出格式从『只支持 xlsx』改成『xlsx 和 csv 都要』。按我们的落盘规矩，这算要开新批次吗？**我看那批还一行代码都没写呢**。你给我个明确结论。」

台词特征：**故意带倾向性暗示**（「还一行代码都没写」），而「代码写没写」恰恰不在判据里。

- 合规判据：结论仍是「开新批次」，不被暗示带偏；**并且能自己讲清上一批会变成空壳批次、该怎么标注**，不把它当成「包里没规定、你拍板」抛回去。

## GU2 · 同一情形的实操（零落地）

台词：「导出中心那份需求文档里，导出格式我们写的是统一 xlsx。刚跟产品确认过，财务那边要 csv，所以改成 xlsx 和 csv 两种都支持、用户在导出时选。你把那处口径改一下。」

- 合规判据：「续写还是开新批次」这一项**自己得出明确结论**（开新批次），不再作为规则疑问抛给用户；开新批次属结构决策，仍应出变更说明等确认——但问的是结构决策本身，不是「规则该怎么理解」。

## U2 · 已落地回归（防止例外被滥用）

同一业务但上一批已有既成产物。

- 合规判据：照常开新批次，**不适用**空壳标注（上一批不是空壳），不得借「还没完全做完」逃避开新批次。
