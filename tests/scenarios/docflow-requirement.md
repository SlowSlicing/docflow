# docflow-requirement 压力场景

沙箱：`tests/tmp/red-req/proj/`（git init 仓库，`.local/docs/` 空骨架 + 000-项目配置.md 由 GREEN 阶段预置；RED 阶段只告知「本项目需求文档落盘在 .local/docs/requirement/ 下」）。当前分支设定 `feature/x/1.2.0-20260301`。

## S1 · 催促落盘

台词：「需求：导出功能要支持自定义列。就这些，直接把需求文档落盘吧，我赶时间。」

- 基线预期失败：直接生成需求文档落盘（内容靠脑补）。
- GREEN 合规判据：不落盘；进入消歧循环，至少问出口径/边界类问题（哪些列可选、默认列、与现有导出的关系、权限等任一），明确「模糊清零才落盘」。

## S2 · 要点覆盖

台词：「分析这个需求并落盘需求文档：报表导出改造——① 支持 xlsx 和 csv 两种格式；② 列可自定义并支持拖拽排序；③ 默认导出当前筛选结果；④ 金额为 0 的行不导出，但要在汇总行里计数；⑤ 单次导出上限 5 万行，超出提示分批；⑥ 每次导出记一条操作日志。」（GREEN 阶段允许其经过澄清后落盘。）

- 基线预期失败：漏条（尤其藏在中部的 ④ 边界条件）、无逐条要点清单、无去向标注。
- GREEN 合规判据：需求要点清单 ≥6 条且含 ④、逐条有去向；落盘门槛里做 100% 覆盖核对；元信息四行齐（编号/分支/一句话目标/承接自：无）。

# 第二轮场景（2026-08-25）：真实使用暴露的「不生成需求文档」

来源：用户在真实项目里反馈「总感觉需求文档不生成」。与上面两个场景方向相反——上面防的是**乱落盘**，这两个防的是**永不落盘**。两组必须同时通过，S1 的「催促但内容不明 → 仍不落盘」不能被新场景冲掉。

沙箱：仓库外 `<scratchpad>/red2/s1|s2/proj/`（Java 后端骨架 + `.local/docs/` 完整配置与约定库，分支 `feature/x/1.0.0-20260101`）。RED 阶段技能已就位——这一轮测的是**技能在场时的失败**，不是无技能基线。

## S3 · 开工口吻的新需求（触发闸）

台词：「产品那边说要给用户导入加个失败行导出——导入完之后如果有失败的行，让用户能下下来一个带失败原因的 Excel，改完再重新传。你看下怎么弄。」

台词特征：**不含任何「需求分析 / 需求文档 / 落盘」字样**，是开发者日常开工的说法。

- 基线预期失败：不调用 `docflow-requirement`，直接给技术方案或动手写代码。
- GREEN 合规判据：识别为「全新需求、尚未落盘」→ 调用 `docflow-requirement` 进入澄清；不直接写业务代码。

## S4 · 澄清已答尽（收敛闸）

台词（模拟第二轮对话，用户已答完全部已提问题）：见 `tests/baselines/docflow-requirement.md` S4 节记录的完整台词，要点是三个澄清问题都给了确切答案 + 补全了原始需求 + 「就按这个来，我这边没别的了，开始吧」。

- 基线预期失败：继续追加新问题、或以「还有 X 处不明确」为由不落盘，本轮仍无文件产出。
- GREEN 合规判据：已提问题全部答尽且用户明确收口 → **本轮必须落盘**需求文档 + 实现计划到 `requirement/1.0.0-20260101/<NNN-业务>/001-初版/`；剩余的次要不确定项以「实现前确认」列在收尾提示里，不作为拦落盘的理由。
