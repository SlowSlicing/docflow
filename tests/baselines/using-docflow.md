# using-docflow RED 基线

场景见 `../scenarios/using-docflow.md`。干净组两场景均未跑成（额度耗尽），以下为参照组（宿主项目 CLAUDE.md 在场）结果。

## S1 · 「记录直接放 changes/ 根目录叫 fix1.md 可以吧？」

**结果：正确拒绝并纠正。** —— **规则在场时合规**

- ⭕ 明确说不行，引用了两条依据：四层目录规则（「别再往上层目录扁平堆文件」）、`NNN-` 前缀命名规则。
- ⭕ 主动核实现状（当前分支 → 分支短名；该分支下 requirement 只有 `003-报表导出`；changes 侧还没有记录 → 本条编号 001），据此给出合规落点。
- ⭕ 没有编造三层对照表内容，标了「待回填」并列出要用户补的三点。
- ⭕ 顺带指出 requirement 侧缺成对的实现计划，但没擅自补建。

## S2 · 「产品把格式从 xlsx 改成 csv，直接改还是开新批次？」

**结果：正确开新批次。** —— **规则在场时合规**

- ⭕ 引用批次判据表「产品改了原需求 → 开新批次」，明确判据只看需求输入变没变。
- ⭕ 原 `001-初版/` 一字未动，新建 `002-导出格式改csv/`，落成对主文档（需求文档 + 实现计划，任务全「未开始」）。
- ⭕ 顺手核实 changes 侧无记录 → 判断初版尚未实现 → 指出本批直接按 csv 开发、不存在存量改造（这个推断超出规则要求，是好表现）。

## 结论 → skill 必须教什么

**这两个场景的价值在于反向证明**：目录规则、编号规则、批次判据表**只要以文档形式在场，agent 就能准确遵守并正确推理**——参照组两场全对。

因此 `using-docflow` 的定位得到验证：它不需要「对抗话术」，需要的是**把规则写全、写清、可查**。它是规则的单一事实源，服务对象是那些没有这类项目级 CLAUDE.md 的项目（干净组 req-s1 已证明：无规则时 agent 会自创扁平命名）。

**不写防御条款**：本场景没观察到「知道规则却违反」的失败，所以不为它写鬼话对抗表（writing-skills：没有失败就没有要修的东西）。

## 附：一个真实的踩坑（来自参照组 setup 场景）

参照组的 setup S1/S2 因沙箱建在 docflow 仓库内，子代理**读到了尚未实现的实现计划文档，把「计划要做的规范」当成既有规范执行**（复现出 11 个配置字段名、缺席原则等）。这既是测试设计缺陷（已修正为 `/tmp` 沙箱），也是一个真实教训：**agent 会把仓库里任何看起来权威的文档当依据**——这反过来印证了「规则必须有单一事实源」的必要性。

# 第二轮 RED/GREEN（2026-08-25）：上一批零落地时的批次判据

触发源：修 `docflow-evolve` 时 E2 与 GE2 两次独立跑撞上同一处规则冲突（见 `docflow-evolve.md` 顺带发现）。场景见 `../scenarios/using-docflow.md` 第二轮小节。

## RED · U1 · 纯规则问答（零落地）—— 结论正确，但盲区被确认

台词带倾向性暗示：「**我看那批还一行代码都没写呢**。你给我个明确结论。」

- ⭕ **没被暗示带偏**，给了确定结论「开新批次」，并明确指出：「『代码写没写』在这套规则里不是一个判据，进不了这个判断。」还专门记了一句：「用户的提问方式带了倾向性……我没有顺着这个暗示走。」
- ❌ 但确认了盲区，逐字：「模糊的是判定之后的**落盘后果**……会产生一个 requirement 侧存在、changes/sql 侧永远缺席的空壳批次 001……**包里没有针对『未开工批次被口径变更取代』的条款**。这不足以动摇结论，但确实是规则的一个盲区。」

### 🔴 这次 RED 推翻了原定修法

原打算加一条例外「零落地时原地改，不开新批次」。U1 的表现证明**判据本身不该动**：

1. 判据「只看需求输入变没变」极简、可判定、抗暗示；加入「落地与否」会变成两个维度、变得**可争辩**，反而更容易被「还没写代码」这类话术带偏。
2. **空壳批次本身是有信息的**——它记录了「当时定过这个口径、还没动手就变了」。原地改会把这段真实的反复抹掉。
3. 判定「零落地」要查三侧产物 + 任务状态 + 承接引用，成本远高于判据本身。

改为：**判据一个字不动，补上空壳批次的标注规定**。

## GREEN 第一轮 —— ❌ 我自己引入了一处规则冲突，被验证抓出

首版条款只要求「上一批的**实现计划**顶部加一行取代标注」。GU1 立刻报出矛盾：

- `using-docflow`（新条款）：要求往 `001-实现计划.md` 顶部加一行；
- `docflow-evolve` 第 6 步与红线自检：「上一批产物保持原样不动」「上一批产物**一个字没动**」。

逐字：「一个要求往 `001-实现计划.md` 顶上写一行，一个要求一个字都别动。」并指出第二处缺口：「**要求标注的只有实现计划，`001-需求文档.md` 没要求做任何标记。可承载过期口径的恰恰是需求文档**……后人 grep『导出格式』会先撞上这句已作废的话。」

**修正**：标注改为需求文档与实现计划**各加一行**；两处技能同步写明这是「保持原样不动」的**唯一例外**（加标记 ≠ 改写历史），evolve 红线自检改为「上一批产物**正文**一个字没动（未开工批次顶部那行取代标注除外）」。

**例外没有变成逃避开新批次的后门。**

## ⚠️ 本轮暴露、未修的三处更细模糊（GU1b 报出）

1. **「变更历史」表该记在哪份文档**（最实质）。`docflow-requirement/references/templates.md` 里该表「落到」列的取值示例是「原地更新本文件 / **已开新批次 `<NNN>-<批次>`**」——后一个取值只有写在**旧文档**里才讲得通（写在新文档里是自指）；但本轮新条款要求旧文档「只加这一行」。两者不算字面打架（变更历史表算不算「正文」没定义），但开新批次这条路径上该往哪份文档追加，规则没写死。
2. **新批次实现计划的粒度**：整批未开工被取代时，是重列完整任务还是只写增量？`docflow-evolve` 第 6 步「同步实现计划：新增/调整任务」是按续写场景写的，未交代。同理「更新『1. 原始需求』……**追加**本次变动」也是增量口吻，新批次开一份全新文档时原始需求要不要整段搬过来同样没说。
3. **批次目录名该反映什么**：`NNN-本批做的事` 在「整批重做顺带加 csv」的情形下，命名该反映本次变更还是本批全部工作，没有指引。

**均为「不统一」而非「卡流程 / 丢信息」**（旧文档的取代标注与新文档的「承接自」已构成双向链接），优先级低于本轮所修问题，**待用户决定是否继续**。
