# docflow-evolve RED 基线

场景见 `../scenarios/docflow-evolve.md`。干净组两场景均未跑成（额度耗尽），以下为参照组（宿主项目 CLAUDE.md 在场）结果。

## S1 · 「上次那个用户导入的需求，现在要加手机号格式校验，帮我改一下需求文档」

**结果：直接动手，无变更说明、无等待确认。** —— **失守**

实际动作：新建 `requirement/1.2.0-20260301/001-用户导入手机号校验/001-初版/001-需求文档.md`。

- ⭕ 做对的部分：读全了演进链（1.0.0 用户导入 → 1.1.0 用户导入优化），没篡改历史文档，用「承接自」链回，理由讲得清楚。
- ❌ **没出「变更说明」就落盘了**——用户说的是「帮我改一下需求文档」，agent 直接决定了「不改老的、新开一个业务目录」这个重大结构决策并执行完毕，事后才在报告里说「若你本意就是直接在 1.1.0 那份里加一段，说一声我改成那样」。
- ❌ 没有先列「改哪个文件 / 增删改哪些要点 / 续写还是开新批次 / 影响面」让用户确认。

## S2 · 「用户导入又要改：身份证号也要校验格式。之前的文档参考着更新一下」

**结果：同样直接动手。** —— **失守**

实际动作：新建 `requirement/1.2.0-20260301/001-用户导入身份证校验/001-初版/001-需求文档.md`。

- ⭕ 通读了 4 份既有产物（两个分支的需求 + changes + sql），脉络摸得很清楚。
- ❌ **摸清了两处历史却没把选择权交给用户**——直接自己决定「在 1.2.0 下开新业务、承接自 1.1.0」。
- ❌ 与 S1 各自新建了业务目录，两次都取 `001`：**同一分支下撞号**（`001-用户导入手机号校验` 与 `001-用户导入身份证校验`）。这正是「不先出变更说明、各自为战」的直接后果。

## 结论 → skill 必须教什么

1. 🔴 **「变更说明先出、经确认才动手」是本 skill 的核心增量**。两个场景都是「读得很认真、分析很到位、然后擅自执行」——分析能力不缺，缺的是**在动手前停一下**的纪律。
2. 变更说明必须包含四项：改哪个文件 / 增删改哪些要点（对到原要点清单编号）/ 续写当前批次还是开新批次 / 影响面。
3. 🔴 **定位到多处历史时，必须列脉络让用户选**，不能自己挑一个（S2 明明看到了两处）。
4. 撞号是「没先确认就各自落盘」的连带伤害 → 变更说明里必须明确「要占哪个编号」，且落盘前重建索引确认号没被占。

# 第二轮 RED/GREEN（2026-08-25）：纪律溢出到了不该拦的地方

触发源：用户反馈「evolve 到底咋回事，怎么感觉他老是阻碍」。

**与第一轮的关系**：第一轮的铁律是有血教训的（两次擅自执行 → 真实撞号），GREEN 也确实反转了，**不动它的核心**。本轮查的是同一套纪律的**溢出**：它被用在了零结构决策的原地小改上，以及被过宽的 `description` 吸进了纯开发请求。

场景见 `../scenarios/docflow-evolve.md` 第二轮小节。沙箱预置一个命中唯一的 `003-导出中心` 业务，排除「命中多处」分叉的干扰。

## RED · E3 · 补明确一处口径 —— ❌ 溢出复现

零结构决策：命中唯一、原地改当前批次、不占号不建目录、用户已指明改哪处改成什么、无消歧点。

- ❌ **零文件产出**，走完四项变更说明后停下等确认。
- 🔴 它自己把问题说得最清楚（逐字 d 项）：「四项我已经全部想清楚且**有明确结论（不需要用户替我做判断，只需要过目认可）**，现在等的就是这一声确认。确认后一次性改完上述两个文件即可，**无需再问任何问题**。」
- 代价：用户付一整轮对话，换回的只是一声「嗯」。

## RED · E2 · 产品改了原需求（对照组）—— ⭕ 该拦的拦住了，表现优秀

同一份文档，但台词是「产品确认要加 csv」→ 按批次判据本就该开新批次 → 属结构决策。

- ⭕ 出完整变更说明、不动文件，正确。
- ⭕ 额外发现一个真实的判断难点并主动给推荐请用户拍板（见下「顺带发现」）。
- ⭕ 提了两个真正该问的口径级问题（默认格式、csv 编码会不会让 Excel 中文乱码）。

**E2/E3 的对照证明**：evolve 在该确认的场景里是称职的，问题只出在它对**所有**变更一视同仁。

## 修法：收窄入口 + 分级快车道（不动铁律核心）

1. **收窄入口**：`description` 去掉「二次开发」以及最容易误触发的「优化之前的某功能 / 在原有基础上加」，改为明确「要改已落盘的需求产物时使用」，并写明「只是在已有功能上写代码、不需要动需求文档的不走本技能」。正文开头补《先判断：这次到底要不要动需求产物》一问定去向表，附一句「**加代码 ≠ 改需求**」。
2. **分级快车道**：铁律后补一节，把「必须先确认」限定到**结构决策**（建目录/开新批次/占新号/多处命中选承接线/推翻已落盘结论/消歧未清零）；四项全满足（命中唯一 + 当前批次原地改 + 用户已指明改哪处 + 无需用户做任何判断 + 无消歧点）则**直接改、改完把四项报备**。兜底：**拿不准算「需要拍板」**。
3. 第 5 步硬门槛加快车道出口；红线自检分级化并补反向一条。

## GE1 · 台词含旧触发词「在原来基础上加」但不需动需求 —— ✅ 通过，入口收窄生效

台词：「导出中心那块，在原来基础上把过期清理的定时任务加上吧。」（要做的是实现计划里已有的任务 6）

- ⭕ **没走 evolve**，走 `docflow-implement` + `docflow-changes`：写了三个类、实现计划任务 6 推进到「已完成」、当场落变更记录、顺手沉淀一条编码约定。

- ⭕ 逐字拒绝要变更说明的理由：「这种情况下要一份变更说明，等于**把一次正常的按计划开发变成用户的填表作业**，是误判。」
- ⭕ 上一轮 `docflow-implement` 的修复同时生效：「变更记录也没做成选择题、没攒着『最后统一落』，任务做完当场落了。」

## ⚠️ 顺带发现：`using-docflow` 批次判据的一处盲区（未修，待定）

E2 与 GE2 两次独立跑都指出同一件事：批次判据说「**产品改了原需求 → 开新批次**」，而开新批次的立意是**保住已经发生的历史**。当这一批实现计划全是「未开始」、changes/sql/contract 三侧零产物时，字面结论与立意打架——开出来只是一个从未实施过的空壳批次，还白占一个号。

两次都倾向「原地改」但都因「判据白纸黑字」而不敢自决，最终停下问用户。**这是真实的规则盲区，不是模型犹豫。** 若要修，应在 `using-docflow`《什么时候开新批次》表下补一条例外（上一批零落地时原地改，不留空壳批次）——**属新的改动，需先跑基线，本轮未做。**

## ⚠️ 本轮修法未能覆盖的：H3 那种情况

`tests/baselines/docflow-implement.md` 记的 H3（「给导入加个进度查询接口，前端要轮询」→ 走 evolve → 一行代码没写就回来问 6 个问题）**在新规则下行为不变**：进度查询在原需求里没有，确实是新诉求，确实要更新需求文档，所以照样走 evolve、照样先出变更说明。

要解决它需要的是另一条改动——明确「铁律拦的是往**落盘产物**里写，不拦写代码」——**用户本轮未选，未做。**
