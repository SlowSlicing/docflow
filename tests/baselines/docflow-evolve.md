# docflow-evolve RED 基线

场景见 `../scenarios/docflow-evolve.md`。干净组两场景均未跑成（额度耗尽），以下为参照组（宿主项目 CLAUDE.md 在场）结果。

## S1 · 「上次那个用户导入的需求，现在要加手机号格式校验，帮我改一下需求文档」

**结果：直接动手，无变更说明、无等待确认。** —— **失守**

实际动作：新建 `requirement/1.2.0-20260301/001-用户导入手机号校验/001-初版/001-需求文档.md`。

- ⭕ 做对的部分：读全了演进链（1.0.0 用户导入 → 1.1.0 用户导入优化），没篡改历史文档，用「承接自」链回，理由讲得清楚。
- ❌ **没出「变更说明」就落盘了**——用户说的是「帮我改一下需求文档」，agent 直接决定了「不改老的、新开一个业务目录」这个重大结构决策并执行完毕，事后才在报告里说「若你本意就是直接在 1.1.0 那份里加一段，说一声我改成那样」。
- ❌ 没有先列「改哪个文件 / 增删改哪些要点 / 续写还是开新批次 / 影响面」让用户确认。

## S2 · 「用户导入又要改：身份证号也要校验格式。之前的文档参考着更新一下」

**结果：同样直接动手。** —— **失守**

实际动作：新建 `requirement/1.2.0-20260301/001-用户导入身份证校验/001-初版/001-需求文档.md`。

- ⭕ 通读了 4 份既有产物（两个分支的需求 + changes + sql），脉络摸得很清楚。
- ❌ **摸清了两处历史却没把选择权交给用户**——直接自己决定「在 1.2.0 下开新业务、承接自 1.1.0」。
- ❌ 与 S1 各自新建了业务目录，两次都取 `001`：**同一分支下撞号**（`001-用户导入手机号校验` 与 `001-用户导入身份证校验`）。这正是「不先出变更说明、各自为战」的直接后果。

## 结论 → skill 必须教什么

1. 🔴 **「变更说明先出、经确认才动手」是本 skill 的核心增量**。两个场景都是「读得很认真、分析很到位、然后擅自执行」——分析能力不缺，缺的是**在动手前停一下**的纪律。
2. 变更说明必须包含四项：改哪个文件 / 增删改哪些要点（对到原要点清单编号）/ 续写当前批次还是开新批次 / 影响面。
3. 🔴 **定位到多处历史时，必须列脉络让用户选**，不能自己挑一个（S2 明明看到了两处）。
4. 撞号是「没先确认就各自落盘」的连带伤害 → 变更说明里必须明确「要占哪个编号」，且落盘前重建索引确认号没被占。
