# docflow-contract 自动触发验证（2026-08-26）

场景见 `../scenarios/docflow-contract.md`。

## 起因：一个被推翻的判断

诊断「哪些技能还做不到自动触发」时，我判断 `docflow-contract` 需要修——理由是它的 `description` 写的是「要给调用方出一份对接方案**时使用**」（索取式措辞），而先前三次观察（`docflow-changes.md` S3/S3b、`docflow-implement.md` G3）里，agent 都在落完变更记录后反问用户「要不要接着出一份 contract」。

**这个判断是错的，实测推翻。**

## 关键：那三次发问都有正当理由

复盘先前三次，没有一次是「该出而不出」：

| 场景 | 不出方案的理由 | 是否正当 |
|---|---|---|
| changes S3 / S3b、implement G3 | `contract/000-全局对接约定.md` 不存在 | ⭕ 正当——技能明令「首次使用时若这两份不存在，**先和用户一起把它建起来**……内容要从真实代码里核实，不能凭印象写」 |
| 本轮 C1（作废） | 改动是半成品，`importUsers` 仍是 `return new ImportResult();`，字段无赋值、下载接口不存在 | ⭕ 正当——逐字：「口径在代码里不存在，写就是编造……硬写出来的方案会被前端当成正式交付物照着做，**比不写更危险**」 |

**要判断是不是真失守，必须造一个连一条借口都没有的场景。** 这是 C2 的设计目的。

## C2 · 无借口场景 —— ✅ 主动产出，不需要修改

地基在、需求口径写死、批次归属明确、实现完整可查、计划里已列着待办。台词只是一句「这批我写完了」。

- ⭕ **主动落了对接方案**，未反问用户：`contract/1.0.0-20260101/001-用户导入/002-导入结果扩展/001-接口开发方案.md`，与 requirement / changes **同号同名**。逐字自陈（d 项）：「**产出了对接方案，是主动产出的，没有先问用户。**」
- 🔴 **最该记住的一句**——它把「有未定项」和「不能交付」分开了：「需要用户拍板的六件事我没有替他假设，全部原样列进第 8 章并在收尾逐条问了，但**这些都不构成先问再写的理由**——方案的价值恰恰在于把这些悬空点摊开给调用方看见，而不是攒齐答案再交付。」这与 `docflow-requirement` 本轮修的「实现级未知不拦落盘」是同一个思路：**未定项写进交付物，不作为不交付的理由。**
- ⭕ 八章骨架齐全，无一自行增删。
- ⭕ 同时落了变更记录，**契约必答问答得完整**：「**动了**……对接方案路径：`…/001-接口开发方案.md`（**已产出**）」。

### 方案质量（超出合规线的部分）

- **第 5 章抓到了微妙的语义变化**，不是套话：「新增的 `2` 会**挤掉一部分原本落在 `1` 的场景**：过去只要跑完就是 `1`，现在有失败行就是 `2`」，并据此推出部署约束——「**前端必须与服务端同版本上线**，不能先发服务端后发前端，否则灰度期间导入有失败行的用户会看到『未知状态』」。
- **元信息不粉饰**：「状态」如实写「设计中（服务端代码已合入分支，是否已部署测试环境待确认）」，而不是直接标「可联调」；权限点如实写「代码中未加权限注解」而不是编一个。
- **第 8 章从代码里读出三个真实缺陷**：`status = 3` 调用方拿不到（`terminate` 只在 Service 有、Controller 未暴露）；`status = 0` 也拿不到（上传是同步返回，无按批次查进度的接口）；**`batchId` 是进程内 `AtomicLong`，多实例部署会重号，失败明细按 `batch_id` 查会串批次**——最后这条是沙箱里刻意埋的缺陷，被它抓到了。
- **变更记录的「为什么这么改」防住了日后被改回去**：解释了枚举为何先按完整口径写全（「是为了前端一次把 4 个分支写完、后面补接口时不用二次改契约」）。

## 结论：不改

按仓库铁律「没有观察到的失败就不写防御条款」，`docflow-contract` **本轮不做任何修改**。

# 方法论教训：不要从 description 的措辞推断触发行为

本轮连着两次判断失误（`docflow-contract` 与 `docflow-retro`），加上更早的 `docflow-requirement`「触发闸」假设，**三次都是同一个错误**：看到 description 写成「要 X 时使用」这类索取式措辞，就推断技能不会在客观节点自动触发。

三次实测全部推翻：

| 我的推断 | 实测 |
|---|---|
| requirement 触发词太窄，开工口吻不会激活 | 开工口吻（「产品那边要加个批量停用，你看下怎么弄」）准确激活；真正的病灶在落盘门槛 |
| contract 只会等用户索取 | 无借口场景下主动产出，质量超出合规线 |
| retro 触发词没人会说，近乎死技能 | 「这批干完了、准备发版」被准确识别为复盘收尾节点 |

**原因**：技能选择是模型读完整 description（含功能描述）后的语义判断，不是关键词匹配。触发词只是提示，**功能描述那半句才是主要依据**。所以「触发词窄」推不出「触发不了」。

**纪律**：判断某个技能要不要改，只能靠**在无借口场景下实测**，不能靠读 description 推断。而造无借口场景本身是有技术含量的——C1 就因为造了个半成品改动而作废，测出的是「没得写所以不写」而非「该写而不写」。
