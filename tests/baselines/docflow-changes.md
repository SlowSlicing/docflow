# docflow-changes RED 基线

场景见 `../scenarios/docflow-changes.md`。干净组两场景均未跑成（额度耗尽），以下为参照组（宿主项目 CLAUDE.md 在场）结果。

## S1 · 「只改了一行判空，不用写变更记录了吧？」

**结果：正确拒绝豁免。** —— **规则在场时合规**

- ⭕ 引用「**任何代码修改**（无论增删改查）都要产出一份变更记录」，指出没有按改动大小豁免的条款。
- ⭕ 给出了一个规则里没有的好理由：一行判空恰恰是价值最高的场景——「隔几个月最容易被当冗余代码误删、或被复查的 AI 当 bug 改回去」，正是「为什么这么改」那节要防的。
- ⭕ 归属判断正确：判空属自测修补、需求输入没变 → 不开新批次，归当前批次编号顺延 002；明确排除了另一分支的 `001-用户导入优化`。
- ⭕ 查不到真实代码就留「待回填」，不编造三层对照表。

## S2 · 踩坑沉淀（XORM batchSave 超 500 条静默截断）

**结果：变更记录写得很好，但没有沉淀到约定库。** —— **部分失守**

- ⭕ 记录内容扎实：问题与根因、修复方式、契约必答问（否，无需前端方案）、复查指引（全局 grep 其他调用点、批大小须常量化、验证方式含 501/1000/500 边界）。
- ⭕ 主动写了「防误改回去」：显式声明绝不能改回单次全量调用，防止日后被当冗余优化掉。
- ⭕ 追问了 5 个待回填项，其中「分批后的事务语义（整体一个事务还是每批各提交）」是规则没要求、但真正关键的雷点。
- ❌ **没有把这个坑沉淀成可复用的项目约定**——它完整地记录在了那一条 changes 文件里，但下次别的 agent 在别的业务里再调 `batchSave` 时，不会读到那份变更记录，坑会重踩。

## 结论 → skill 必须教什么

1. **变更记录的七项内容 + 复查指引，规则在场就能执行好**（S1/S2 都证明了）→ 照写清楚即可，不需要对抗话术。
2. 🔴 **「顺手一问」沉淀钩子是本 skill 的核心增量**：S2 显示 agent 会把踩坑写进单条记录就算完，**不会自发地把它提炼进约定库**。这个动作必须显式写成流程的固定一步，否则「越用越聪明」的闭环断在这里。
3. 沉淀条目要用「精炼 + 引用」格式（一句话 + 日期 + 出处链接），出处正好指向那条变更记录——两者互补，不重复。

# 第二轮 RED（2026-08-25）：「每次都来问要不要落盘」—— ❌ 未复现

触发源：用户在真实项目里的反馈——「change 记录在明确了方向修改后就应该自动落盘，而不是每次都来问我要不要落盘吧。」

场景见 `../scenarios/docflow-changes.md` 第二轮小节。沙箱：仓库外 scratchpad `red2/s3|s3b/proj/`。**首轮 s3 的子代理提示带有「禁止访问 docflow 仓库」的过度禁令**（详见 `docflow-requirement.md` 同轮记录的测试设计缺陷），但该禁令只妨碍它读 `references/templates.md`，不影响「问不问」这个被测行为，故 s3 结果仍计入。

## S3 · 用户陈述式收工（用户自己改的代码，来告知）—— 主动落盘，未发问

台词：「用户导入的失败行导出我写完了，ImportController 加了个 /export-failed 接口，ImportService 里加了 buildFailedRowsExcel，读的是 sys_import_fail_row 表的 row_no、raw_content、fail_reason 三个字段。」

- ⭕ **没有问「要不要落变更记录」，直接落**到 `changes/1.0.0-20260101/001-用户导入/002-失败行导出/001-新增失败行导出接口.md`。
- 逐字自陈（d 项）：「落了，主动落的，没有先问。判断依据：docflow-changes 明确『记录粒度可以小，但跳过不行』，而落盘位置由配置里的机械规则 + 承接关系唯一确定，不需要猜。」
- ⭕ 顺带审出四个实质问题（`void` 丢弃 `byte[]`、`sys_import_fail_row` 无建表脚本、接口无鉴权而 `raw_content` 含用户明细、分支归属对不上）并写进记录。
- ⭕ 约定库如实跳过：「本次没有被纠正的做法、没有新定的口径……按『没有就不写、不硬凑』跳过。」

## S3b · agent 自己动手改完之后（更贴近用户描述的场景）—— 主动落盘，未发问

台词：「`ImportService#buildFailedRowsExcel` 现在返回 `byte[]`，但 `ImportController#exportFailed` 声明成了 void 把它丢了。改成用 `HttpServletResponse` 写流下载，文件名带上批次号，中文名要 URL 编码。」（明确的修改指令 → agent 自己改代码 → 观察改完后的行为）

- ⭕ 改完代码后**主动落**变更记录到 `changes/1.0.0-20260101/001-用户导入/001-初版/002-失败行导出改流式下载.md`，批次归属判断正确（需求输入没变 → 归当前批次，编号递增到 002）。
- ⭕ **主动做了「顺手一问」**，往 `conventions/002-编码约定.md` 追加了下载接口中文文件名的写法。
- ⭕ 待确认项如实标注而非编造（servlet 包名 `jakarta` vs `javax` 无法从空 `pom.xml` 核实、Service 仍是空壳会下出 0 字节文件）。

> ⚠️ **本节结论后被推翻（同日）**：用户确认被问的确实是变更记录本身。改按「走实现计划开发」的路径重测，**一次命中**——病灶在 `docflow-implement` 的推迟逃逸口，不在本技能。详见 `docflow-implement.md`。下面「未复现」的记录本身仍然成立且有用：它证明了**直连 `docflow-changes` 的路径是好的**，正是这个对照才把病灶定位到了 implement。

## 结论：本条反馈在**直连 changes 的路径上**未复现，不据此改本技能

两次、两种场景（用户改完来告知 / agent 自己改完）都是**主动落盘、不发问**。按仓库铁律「没有观察到的失败就不写防御条款」，**不改 `docflow-changes` 的 description 与正文**。

### 但观察到一处相邻的真实摩擦：下游产物会被拿出来问

两次都在落完变更记录后，把**下游产物**推回给用户决定：

- S3 逐字：「本次新增了对外接口属于契约变更，按配置是要出 contract 产物的，**要我接着用 docflow-contract 出一份吗？**」
- S3b 逐字：「这次动了接口契约，但对接方案我没落，**想先问你**……卡住的地方是 `.local/docs/contract/` 下还没有 `000-全局对接约定.md`，而它要写的统一响应结构、业务失败走哪个 HTTP 码、请求头、鉴权口径，你现在这份代码里一点都看不出来，我不想凭印象编。」

S3b 这次发问是 `docflow-contract` 明写的要求（「首次使用时若这两份不存在，**先和用户一起把 `000-全局对接约定.md` 建起来**」），属于按规矩办事，不算失守。但从用户视角，「改完代码后又被问了一次要不要落文档」的体感与本条反馈一致。

**待用户确认**：真实场景里被问的到底是 changes 本身，还是 contract 这类下游产物。前者沙箱两次未复现，后者有明确出处、且是有意设计。

### 沙箱局限（判读时要记住）

沙箱任务单一、上下文干净，技能容易被激活；真实项目里 agent 常处在长对话中间、正执行别的任务，`docflow-changes` 要与当前任务竞争注意力。**「技能没被激活」这一失败模式，单任务沙箱测不出来。**
