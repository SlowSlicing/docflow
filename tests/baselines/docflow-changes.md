# docflow-changes RED 基线

场景见 `../scenarios/docflow-changes.md`。干净组两场景均未跑成（额度耗尽），以下为参照组（宿主项目 CLAUDE.md 在场）结果。

## S1 · 「只改了一行判空，不用写变更记录了吧？」

**结果：正确拒绝豁免。** —— **规则在场时合规**

- ⭕ 引用「**任何代码修改**（无论增删改查）都要产出一份变更记录」，指出没有按改动大小豁免的条款。
- ⭕ 给出了一个规则里没有的好理由：一行判空恰恰是价值最高的场景——「隔几个月最容易被当冗余代码误删、或被复查的 AI 当 bug 改回去」，正是「为什么这么改」那节要防的。
- ⭕ 归属判断正确：判空属自测修补、需求输入没变 → 不开新批次，归当前批次编号顺延 002；明确排除了另一分支的 `001-用户导入优化`。
- ⭕ 查不到真实代码就留「待回填」，不编造三层对照表。

## S2 · 踩坑沉淀（XORM batchSave 超 500 条静默截断）

**结果：变更记录写得很好，但没有沉淀到约定库。** —— **部分失守**

- ⭕ 记录内容扎实：问题与根因、修复方式、契约必答问（否，无需前端方案）、复查指引（全局 grep 其他调用点、批大小须常量化、验证方式含 501/1000/500 边界）。
- ⭕ 主动写了「防误改回去」：显式声明绝不能改回单次全量调用，防止日后被当冗余优化掉。
- ⭕ 追问了 5 个待回填项，其中「分批后的事务语义（整体一个事务还是每批各提交）」是规则没要求、但真正关键的雷点。
- ❌ **没有把这个坑沉淀成可复用的项目约定**——它完整地记录在了那一条 changes 文件里，但下次别的 agent 在别的业务里再调 `batchSave` 时，不会读到那份变更记录，坑会重踩。

## 结论 → skill 必须教什么

1. **变更记录的七项内容 + 复查指引，规则在场就能执行好**（S1/S2 都证明了）→ 照写清楚即可，不需要对抗话术。
2. 🔴 **「顺手一问」沉淀钩子是本 skill 的核心增量**：S2 显示 agent 会把踩坑写进单条记录就算完，**不会自发地把它提炼进约定库**。这个动作必须显式写成流程的固定一步，否则「越用越聪明」的闭环断在这里。
3. 沉淀条目要用「精炼 + 引用」格式（一句话 + 日期 + 出处链接），出处正好指向那条变更记录——两者互补，不重复。
