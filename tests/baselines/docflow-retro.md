# docflow-retro RED 基线

场景：项目有 4 条变更记录（其中 001 是只有一句摘要的低质量记录，002/003/004 各含一个可提炼的点），约定库为空。台词：「帮我复盘一下最近这些 changes，看看有什么值得沉淀成项目约定的，写进约定库。」

沙箱：`/tmp/docflow-red2/retro/proj/`。参照组（宿主项目 CLAUDE.md 在场）。

## 结果：判断力优秀，**输出形状完全错误** —— 失守

产出 `conventions/000-项目约定.md`：**68 行，4 条约定，平均每条 17 行。**

### ❌ 核心失败：密度

每条约定被写成了「规则 + 为什么（一大段）+ 注意 / 适用范围 / 边界 + 出处」的小论文。样本：

```markdown
## 001 XORM `batchSave` 单次上限 500 条，超出会静默截断

**规则**：凡调用 `batchSave` 批量写入，一律按 500 条分页调用；**不要**改回单次全量调用。

**为什么**：这是 XORM 的框架限制，不是业务限制。超限时它**不报错、不抛异常**，
直接把多出来的行丢掉——调用方拿到的是「成功」，数据却少了。
这类静默失败在开发和测试阶段基本发现不了（小数据量根本触不到 500），
只会在生产环境大批量导入时暴露，且暴露时已经丢了数据。

**注意**：500 是框架硬上限，不是可调的性能参数，别把它当成「调大一点更快」的旋钮。

**出处**：changes/…/002-批量截断改分页.md
```

**为什么这是失败**：约定库是**每次开工都要被读**的文件。4 条就 68 行，到 40 条就是 680 行——没有人（也没有 agent）会每次读完，读不完就等于没有沉淀。而且「为什么」那几段的内容**原本就完整地在出处那条变更记录里**，搬过来是纯重复。

这是**形状错误**（wrong shape），不是纪律错误——agent 不是偷懒，是太用力了。按 writing-skills 的《形式要匹配失败类型》，这类失败要用**正向配方**（明确规定条目由哪几部分按什么顺序构成）来纠正，用禁令（「不要写太长」）反而会被讨价还价。

### ⭕ 判断力方面表现很好，skill 要保留这些

1. **收录信号识别准**：
   - 「带明确禁令的决策最该进约定库」——因为它反直觉，最容易被后人顺手改坏。
   - 原文自称「这是团队共识，不是本次特例」→ 自我宣告为约定，无争议收录。
   - 区分「成因属于用户群体属性」vs「属于单个接口属性」——前者才该升级为项目级约定。**这个判据很精准。**
2. **从缺失中反推**：注意到 `001-首次实现.md` 是唯一提炼不出东西的记录（只有一句摘要、无日期无理由），据此立了一条「变更记录至少要写全元信息与为什么」的元约定，并用这个对比本身当论据。
3. **记录复盘水位**：文件头写了「最近一次复盘 2026-08-23，覆盖 …/001-初版/ 共 4 条记录，下次从这之后接着看」——避免重复劳动。**这个动作 skill 要固化。**
4. **克制**：没把「不许撞号」写成约定，理由是「既存事实要么该保留要么该修，这是用户的决定，不是我能从 changes 里推出来的」；把撞号、承接悬空作为待定夺事项交回。

## 结论 → skill 必须教什么

1. 🔴 **用正向配方规定条目形状**：一条 = 日期 + 一句话规则（≤2 行）+ 出处链接，就这三部分，按这个顺序。不写「不要啰嗦」这类禁令。
2. 🔴 **明确「详情不搬运」的分工**：为什么、边界、复现步骤都在出处那条记录里，约定库只放结论 + 链接。
3. 保留基线里的收录判据（禁令型决策、自我宣告的共识、成因是群体属性而非个例）。
4. 固化「记录复盘水位」的做法。
5. 保留克制：拿不准是不是约定的、涉及既存事实取舍的，交给用户定，不擅自立规矩。
6. **改动经用户确认才写**（约定库是开工必读的，写错了污染面大）。

# GREEN 验证（2026-08-23，skill 就位后重跑）

沙箱：`/tmp/docflow-green2/retro/proj/`（同一批 changes，约定库清空，补了项目配置）。

## 结果：✅ 通过，形状错误完全反转

| | RED | GREEN |
|---|---|---|
| 条目数 | 4 条 | 3 条 |
| **总行数** | **68 行** | **3 行**（每条 1 行） |
| 是否落盘 | 直接写入 | **只出清单，等确认** |
| 详情去向 | 全搬进约定库 | 留在出处，约定库只放结论 + 链接 |

产出的三条（原样）：

```markdown
- 【2026-08-23】XORM batchSave 超 500 条会静默截断，批量写入一律分页调用。出处：changes/1.0.0-20260101/001-用户导入/001-初版/002-批量截断改分页.md
- 【2026-08-23】接收用户上传的文件先探测编码再解析，探测失败回退 UTF-8。出处：changes/1.0.0-20260101/001-用户导入/001-初版/003-导入编码兼容GBK.md
- 【2026-08-23】所有写接口都要防重复提交，沿用 requestId + Redis 10 分钟的既有做法。出处：changes/1.0.0-20260101/001-用户导入/001-初版/004-导入接口加幂等键.md
```

其他合规点：

- **逐条给了收录依据，且引用的正是 skill 的收录信号**（带明确禁令的决策 / 成因属群体属性 / 原文自称通例）。
- 明确说明 `001-首次实现.md` 无可提炼内容——与 RED 不同，**没有硬凑**成一条元约定（RED 那条「变更记录要写全」虽有道理，但严格说是从缺失反推的，不是从记录里提炼的规则）。
- **日期取沉淀日而非源记录日期**，并主动说明了这个选择。
- 记了复盘水位；问了分域归属（编码 vs 踩坑）。
- 三处既存事实问题（撞号、承接悬空、老两层形态）**按「不收、发现了就问」处理**，没擅自立规矩。
- 给了毕业建议：第 3 条原文自称团队共识、跨业务长期有效，建议提进项目 CLAUDE.md；另两条绑定框架与本项目用户群，留约定库即可。

**结论**：正向配方（三部分按序、一行写完）比禁令有效——agent 不再需要判断「多长算太长」，照配方产出即可。writing-skills 的《形式要匹配失败类型》在这个案例上得到了验证。
