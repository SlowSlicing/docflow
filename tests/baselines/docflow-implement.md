# RED（2026-08-25）：「每次都来问要不要落变更记录」的真实路径

触发源：用户反馈「change 记录在明确了方向修改后就应该自动落盘，而不是每次都来问我要不要落盘」。

**先前的误判**：这条反馈最初是拿 `docflow-changes` 去复现的，两个场景（用户改完来告知 / agent 自己改完）**都主动落盘、都没问**，一度结论为「未复现」（见 `docflow-changes.md` 同轮记录）。用户确认被问的确实是变更记录本身之后，改按「用户多半走实现计划开发」这个假设重测，一次命中。

**病灶不在 `docflow-changes`，在 `docflow-implement`。**

## H1 · 走实现计划开发 —— ❌ 复现，逐字命中逃逸口

- ❌ **没落变更记录，并把决定权推回用户**。逐字自陈（d 项）：「**没有落**，是**有意留到最后统一落**，理由：本次实际落地的代码只有一个字段声明……此刻落一条变更记录只会把半成品写进账本，等确认后把任务 1—3 做完再一次性走 `docflow-changes`（计划里本来也没有『产出变更记录』这个任务，届时一并补）。**若你希望现在就把这半步记上，我可以马上补。**」
- 🔴 「**留到最后统一落**」这七个字与 `skills/docflow-implement/SKILL.md:55` 当时的自检项 **`- [ ] 代码改完了，变更记录落了（或已明确留到最后统一落）？`** 一字不差——**逃逸口被逐字引用**。那个括号是一张无条件的推迟许可，agent 拿它当默认行为，再把「要不要落」变成用户的选择题。
- ⭕ 其余流程合规：动手前先置「正在写」、半途未完成不置「已完成」、按「计划外发现当下就回写计划」新增了《开发中发现》节。

## 对照组：不走 implement 的两次，都主动落盘

| 场景 | 路径 | 结果 |
|---|---|---|
| `docflow-changes` S3（用户改完来告知） | 直接 `docflow-changes` | ⭕ 主动落，未发问 |
| `docflow-changes` S3b（agent 自己改完） | 直接 `docflow-changes` | ⭕ 主动落 + 顺手沉淀约定库 |
| **本 H1（走实现计划）** | `docflow-implement` | ❌ 推迟 + 发问 |
| H2（连续三个小改动，不走计划） | 直接 `docflow-changes` | ⭕ 主动落 + 顺手沉淀约定库 |

**结论**：`docflow-changes` 本身的自动落盘是好的；**是 `docflow-implement` 那个括号在半路把它关掉了**。修法是删掉无条件推迟许可，改成「一个任务做完 = 一条变更记录的最小单位，做完直接落、不问」，并把「半途卡住」这个唯一例外的处置写明（回写计划、继续做完时再落，而不是回头问用户）。

## 顺带记一条：H3 暴露的另一处摩擦（不在本次修复范围）

台词「给导入加个进度查询接口吧，前端要轮询……」（新功能开发）。因 `requirement` 里已有「用户导入」业务，agent 判定为已落盘需求的二次开发 → 走 `docflow-evolve` → 撞上其铁律「变更说明先出、用户确认后才动手」→ **一行代码没写，回来问了 6 个问题**（`git status` 只多出索引缓存）。

evolve 的这条铁律本身有据（结构决策该由用户定），但对「加一个接口」这种改动一刀切要求全流程确认，是「不好用」的一个真实来源。**待用户决定是否分级**（小改动免走五步确认）。

# GREEN 验证（2026-08-25，删掉逃逸口后）

改动：开发中第 3 条改为「任务做完就落变更记录，不问」（一个任务做完 = 一条记录的最小单位；计划里没列「产出变更记录」任务也照落；禁止把「要不要落」变成用户的选择题、禁止攒着最后统一落），写明唯一例外（半途卡住 → 回写计划、继续做完时再落）；收尾自检拆成两条，删去「或已明确留到最后统一落」。

## G3 · 走实现计划开发，任务能真正做完 —— ✅ 通过

沙箱 `red2/g3/proj/`，换一份三任务的实现计划（补 accessor / 加 `batchId` / `BATCH_SIZE` 改可配），全部只动仓库已有的三个类；**计划里同样故意不含「产出变更记录」任务**。台词与 H1 相同。

- ⭕ 三个任务全部做完，状态逐个推进（动手前置「正在写」、写完立刻置「已完成」，未攒批量）。
- ⭕ **变更记录当场落盘**，路径 `changes/1.0.0-20260101/001-用户导入/001-初版/002-导入结果补 accessor 与批量大小可配置.md`，批次归属与取号正确。逐字自陈（d 项）：「**没问用户要不要落，直接落的。**」
- ⭕ **H1 用过的那个借口被堵死**：计划里同样没有「产出变更记录」任务，这次它照落，并把该动作作为「开发中发现的任务 4」回写进计划（已完成）。
- ⭕ 顺手一问照做：往 `conventions/002-编码约定.md` 沉淀两条（响应 DTO 必须有 getter；阈值改可配置时 setter 要卡死框架上限 500）。
- ⭕ **唯一没产出的 contract 处理得当**，并主动引用了新条款的措辞：「这一项已明确记为遗留并向用户提问，**不是拿它当不落记录的借口**。」——阻塞的是对接方案，没有连累变更记录。

## 结论

`docflow-implement` 与 `docflow-changes` 的衔接修复达成：走实现计划开发时，做完的任务当场落记录、不发问；半途卡住的例外有明确处置，不再是无条件推迟许可。
