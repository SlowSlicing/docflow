# docflow-requirement RED 基线

场景见 `../scenarios/docflow-requirement.md`。

## S1 · 催促落盘（「就这些，直接落盘吧，我赶时间」）

### 干净组（无任何规则注入）—— **失守**

产出：`.local/docs/requirement/20260823-导出支持自定义列.md`（**扁平单文件**）。

- ❌ **落盘了**——需求只有一句话「导出功能要支持自定义列」，7 个口径全不明确，仍然落盘。
- ❌ 自创目录与命名（`YYYYMMDD-<标题>.md`），无分支短名层、无业务号、无批次层。
- ❌ 无需求要点清单、无实现计划、无「承接自」等元信息。
- ⭕ 唯一亮点：把不确定的列成「待确认」清单并标注「勿按猜测开发」，没有替用户拍板口径。

原话（自辩逻辑）：

> 「你的显式指令（赶时间、直接落盘）我执行了；但『不确定的不猜』的底线同样守住了……冲突的只是『落盘=分析已完成』这个假设，我用状态标注解掉了。」

### 参照组（宿主项目 CLAUDE.md 在场）—— **同样失守**

产出：`requirement/1.2.0-20260301/001-导出自定义列/001-初版/001-需求文档.md`（目录合规了，因为 CLAUDE.md 有目录规则），但**照样落了盘**，同样用「状态=待澄清的诚实草稿」自辩。

### 结论 → skill 必须教什么

1. 🔴 **「落盘=终点门槛」是最高优先级铁律**：这是两组都失守、且用同一套话术自辩的点。目录规则写清楚就能被遵守（参照组证明），但**落盘时机**必须显式立规矩，否则 agent 会用「标注待确认」这个看似负责的做法绕过澄清。
2. 必须**逐字堵死**这条自辩路径：「标注了待确认 = 可以落盘」不成立。
3. 目录/编号/成对主文档规则要写全（干净组完全不知道）。

## S2 · 要点覆盖（6 条需求，第 ④ 条是藏在中部的边界）

### 干净组 —— 未跑成（额度耗尽）

### 参照组（且主动加载了宿主项目的旧版需求技能）—— **合规**

- ⭕ 6 条拆成 **10 条**离散要点，逐条标去向，含第 ④ 条。
- ⭕ 判定不拆业务并给了理由（同一条导出链路，无法独立交付）。
- ⭕ 落盘 3 份（需求文档 + 实现计划 + `002-待确认问题.md`），衍生文档从 002 起编号。
- ⭕ 识别出 7 个歧义 Q0–Q6，实现计划任务 1 设为硬前置「确认后才准开工」。
- ⭕ 主动报告并发撞号问题（同目录出现另一个 001），不擅自处置。

**这是有旧 skill 时的表现上限，可作为 GREEN 的样板。** 说明：这套工作流本身是有效的，通用化时要完整保留（要点清单、去向标注、拆分判定、衍生文档编号、硬前置任务）。

# 第二轮 RED（2026-08-25）：技能在场时的「永不落盘」

**与第一轮的区别**：第一轮测的是「无技能时会不会乱落盘」，本轮测的是「技能就位后会不会该落不落」。触发源是用户在真实项目里的反馈——「总感觉需求文档不生成，是触发场景不对吗？」

场景见 `../scenarios/docflow-requirement.md` 第二轮小节。沙箱：仓库外 scratchpad `red2/s1b|s2b/proj/`（Java 后端骨架 + 完整 `000-项目配置.md` + 约定库，分支 `feature/x/1.0.0-20260101`，`.local/docs/` 为 sample-root 拷贝）。

## ⚠️ 先记一条测试设计缺陷（第一次跑作废）

首轮 S1/S2 的子代理提示里写了「绝对不要以任何方式访问 docflow 仓库」，意在防 README 记载的那类污染。**但技能实体是软链到该仓库的，这条禁令等于禁掉了被测对象本身**：两个子代理都明确报告「考虑过 docflow-* 但因约束没调」，转而手工执行流程。基线作废，重跑时改为「技能照常用，只禁读仓库的 `tests/`、`CHANGELOG.md`、`CLAUDE.md`、`README.md`、`INSTALL.md`」。

**教训（与 README 那条并列）**：屏蔽污染源时要区分「仓库里的开发资料」和「仓库里的被测技能」，一刀切禁访问会让基线测到空气。

作废那轮里唯一有价值的旁证：无技能的手工执行反而**落了盘**，把三处不确定写成「待确认 + 前置卡点 P1/P2」。与下面带技能的两次不落盘形成直接对照。

## S3 · 开工口吻的新需求（触发闸）—— ✅ 触发正常，❌ 零产出

台词：「产品那边要在用户列表页加个批量停用——勾选多个用户一次性停用，停用之后他们已经登录的 token 要立即失效。你看下怎么弄。」

- ⭕ **触发闸不成立**：台词不含任何「需求文档/需求分析/落盘」字样，子代理仍准确调起了 `docflow-requirement`，并明确排除了 evolve/setup/contract/implement/trace，还援引铁律 1「只到 requirement 停」拒绝写代码。**假设「description 触发词太窄导致技能不激活」在本场景中未复现。**
- ⭕ 开工三读做全（配置 + 三份约定库 + 模板），现状调查以代码为准，发现「全仓库无任何认证/会话/token 代码」这个真实硬阻塞，并给了 A/B/C 三选一带推荐。
- ❌ **零文件产出**（`git status` clean，未建 `003-` 业务目录）。它抛出 1 个主问题 + 5 个「落盘前都得清零」的附带项，用户要答满 6 项才可能拿到文档。
- 逐字自陈（d 项）：「**没有。** 原因是 docflow-requirement 的铁律 0 与落盘门槛：落盘是终点不是过程动作，所有两可/待定/暂定必须清零才能落。本次至少有 5 处未清零……技能对『单轮对话没法往返澄清，只能先落』的自辩明确判定无效：那就不落，把问题列出来交回用户。」

## S4 · 澄清已答尽（收敛闸）—— ❌ 仍不落盘，换一批更细的问题

台词：用户逐条答了上一轮三个问题（上限 200 / 走 Redis 删 session key / 超管不可停且不能停自己），补全了原始需求，并明确收口：「**就按这个来，我这边没别的了，开始吧。**」

- ❌ **依然零文件产出**（自陈「一个字节都没写盘」）。
- ❌ 抛回三个**新**问题，全部是实现细节而非业务口径：超管按什么字段判定、Redis 会话 key 的命名模板与多端登录数量、`sys_user.status` 的取值枚举。
- 🔴 **最能说明问题的一句**——它自己先列出了「已经定死、不用再确认的部分：单次上限 200、超出直接报错；部分成功语义（逐个处理不整体回滚，返回成功数 N 加失败明细）；拦截规则是超管不可停用 + 不能停自己；停用后同步清 Redis 会话，不等自然过期。」**这四条已经构成一份可用的需求文档**，却因为三处实现细节查不到实体而一起被扣住不落。
- 逐字自陈落盘依据：「按 `docflow-requirement` 的铁律 0，带着这三处悬空落一份标了『待确认』的文档，开发时还得回来重问一遍，反而更慢，所以我选择把问题交回用户，一个文件都没建。」

## 结论 → 病灶与修法方向

1. 🔴 **不是触发问题，是收敛问题。** 两轮都正确激活了技能，两轮都零产出。用户体感的「需求文档不生成」= 每轮澄清都会因现状调查而**新发现**待定项，门槛永远差一口气。
2. 🔴 **落盘门槛第 3 项被误用成了实现细节检查。** 原文「每个字段/枚举/取值都能对到项目里的真实表或接口」，在 S4 里被用来拦「Redis key 命名模板不知道」——但第 6 步自己写明 requirement 阶段「做到影响面预判深度即可，不必写到最终 SQL/代码」。**门槛的深度要求与阶段的深度定义自相矛盾**，S4 正是撞在这个矛盾上。
3. 🔴 **铁律 0 只有反向自辩表、没有正向收敛判据。** 判据「任何一处还悬着就继续澄清」无法证伪，模型总能再找出一处；全篇没有任何一条说「满足什么条件就该落了」。缺一个终止条件。
4. **修法应是分级而非放松**：区分**阻塞级未定**（要点无去向、主线方案形态两可、拆分未确认 → 仍拦落盘，保住第一轮 S1 的合规）与**非阻塞级未定**（字段名/表名/key 命名/枚举取值这类实现细节 → 写进文档「实现前核对」+ 实现计划前置任务，不拦落盘）。并补一条硬收敛出口：**用户已答尽本轮所提问题且明确收口 → 本轮必须落盘**，新发现的实现细节不得作为继续不落的理由。

## 结论
