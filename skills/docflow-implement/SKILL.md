# 按实现计划开发

实现计划不是写完就扔的清单，它是**进度的唯一真相**。对话被截断、机器重启、隔了三天回来——靠它接上。

**REQUIRED BACKGROUND:** 总规则见 `using-docflow`；计划模板见 `docflow-requirement/references/templates.md`。

## 三种状态，只用这三种

| 状态 | 含义 |
|---|---|
| **未开始** | 刚计划好，完全没有实施 |
| **正在写** | 准备写这个任务的代码了——**先改状态，再动手** |
| **已完成** | 这个任务的代码已经写好 |

## 更新时机（关键）

```
置「正在写」→ 写代码 → 置「已完成」→ 下一个任务
```

- **动某任务前先置「正在写」**——先落盘再动手。顺序反了，中断就丢进度。
- **写完立即置「已完成」**。
- **一个任务一改，别攒着批量更新。** 攒到最后一把改，等于没维护——中断恰恰发生在「攒着」的那段时间里。

## 中断恢复：先复验，再续写

隔了一段时间回来，或者不确定上次改到哪了：

1. **读实现计划**，找出所有标着「正在写」的任务。
2. **对照真实代码复验每一个**——那个任务的代码到底写了没有、写了多少？
   - 已经写完了 → 改成「已完成」。
   - 写了一半 → 判断是续写还是回退重来，跟用户说明现状再动手。
   - 完全没动 → 改回「未开始」。
3. 复验完了才继续后续任务。

**为什么必须复验**：极端情况下改到一半没来得及更新状态，「正在写」这个标记只说明「曾经打算写」，不说明写到哪了。**不复验就往下做，会重复劳动或跳过缺口。**

## 开发中的三件事

1. **计划外的改动要回写计划**：开发中发现漏了任务、或者方案变了，**当下就更新计划正文**（加任务 / 改任务描述 / 标注为什么变），别攒到最后。计划要始终反映真实的「要做什么」。
2. **需求本身变了 → 不是这里处理**：那是 `docflow-evolve`，走变更说明流程。计划只反映「怎么做」，需求变动要先在 requirement 侧定案。
3. **任务做完就落变更记录，不问**：**一个任务做完 = 一条变更记录的最小单位**，做完直接转 `docflow-changes` 落盘。计划里通常有一个「产出变更记录」任务，落完再把它置「已完成」；**计划里没列这个任务也照落**。

   🔴 **不要把「要不要落」变成用户的选择题**，也不要攒着「最后统一落」——攒着和不落是一回事：中断恰恰发生在攒着的那段时间里，攒到最后往往是一条都没有。

   **唯一可以不落的情况**：任务卡在半途——代码只写了一半，或方案本身还等用户拍板，此时改动不构成一次可交付的变更。那就把现状回写进计划，**继续做完时再落**——不是回头问用户「要不要现在补一条」。

   ⚠️ **「代码写完了，等用户自测/验证」不算半途**，那是完整的一次改动，当场落。验证真发现问题就再落一条标「修正 NNN」的记录（`docflow-changes` 有这个机制接住），而不是让记录一直等在验证后面。

## 收尾自检

- [ ] 每个动过的任务，状态都是当下改的，不是最后补的？
- [ ] 没有任务停留在「正在写」却其实已经写完？
- [ ] 开发中新增/调整的任务已经回写进计划？
- [ ] 需求层面的变动没有偷偷写进计划（那要走 `docflow-evolve`）？
- [ ] 每个**做完**的任务，变更记录都当场落了——没推给用户决定，也没攒着「最后统一落」？
- [ ] 卡在半途的任务，现状回写进计划了（而不是拿它当不落记录的理由）？**「等用户自测通过」不算半途。**
