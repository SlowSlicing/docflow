# 对接方案

给调用方的**正式交付物**，不是草稿。写完把路径给用户，由他转交。

**REQUIRED BACKGROUND:** 目录与编号规则见 `using-docflow`。模板见 `references/templates.md`。

## 先确认这两件事

1. **项目配置启用 contract 了吗**？没启用就不适用——问用户是不是要启用。
2. **目录名映射**：存量项目可能把这类产物叫别的名字（如 `frontend`），按配置里登记的目录名落，别新建一套。

## 落盘

```
<落盘根>/<contract 目录名>/<分支短名>/<NNN-业务>/<NNN-批次>/001-接口开发方案.md
```

- 主文档固定 `001-接口开发方案.md`；衍生（字段字典、迁移清单）从 `002` 起。
- 业务号、批次号与 requirement / changes **同号同名**。

## 两份常驻文档（在 contract 根，`000-` 前缀 = 不属于任何分支）

| 文件 | 作用 |
|---|---|
| `000-全局对接约定.md` | 请求头、统一响应结构与状态码、**业务失败走哪个 HTTP 码**、分页参数、日期格式、鉴权与权限口径、以及本项目特有的坑。**跨批次不变**，每份方案顶部引用它即可，**不要在方案里重复抄** |
| `000-方案模板.md` | 写方案时复制它再填 |

首次使用时若这两份不存在，**先和用户一起把 `000-全局对接约定.md` 建起来**——它是所有方案的地基，内容要从真实代码里核实（响应结构、状态码、请求头），不能凭印象写。

## 八个章节（别自行增删）

| # | 章节 | 硬要求 |
|---|---|---|
| 1 | 元信息 | 批次 / 关联需求 / 分支 / 环境 / 契约载体分组 / **状态** |
| 2 | 这批给调用方带来什么 | 一段话说清，让人不用读完全文也知道要不要动 |
| 3 | 接口清单表 | 路径 · 方法 · 增改废 · 用途 · 权限点 |
| 4 | 逐接口详述 | 请求字段 · 响应字段 · 业务异常 · 注意事项 |
| 5 | **破坏性变更与迁移** | 旧→新对应、下线时间、调用方要改哪些页面。**漏了就是线上事故** |
| 6 | 调用方待办清单 | 多端并行的项目（如 PC + 移动端）**每一端都要列** |
| 7 | 联调准备 | 测试环境/账号、需要的权限、造数说明 |
| 8 | 未定 / 待确认 | **漏了调用方就得靠猜** |

## 硬要求

- **不留 `TBD`、空表、`<占位>`**——没有的写「无」。
- **状态字段要真实**：`设计中`（签名还会变，调用方别写死）→ `可联调`（已部署测试环境）→ `已上线`。
- **口径以代码为准**，不要凭印象写。
- **受静默过滤影响的接口必须在「注意事项」点明**（比如数据权限会让返回行数变少）——否则调用方会把「行数不对」当 bug 查半天。
- 若项目有独立的契约载体（Swagger / Apifox / OpenAPI 文件），**方案不重复抄字段表**，而是确认载体里的描述已更新，方案只写「这批怎么改、什么口径、要动哪些页面、怎么迁移」——那些是载体表达不了的。

## 收尾

告知路径，提示用户转交调用方。若 requirement 侧的实现计划里有「产出对接方案」任务，同步标记完成。
