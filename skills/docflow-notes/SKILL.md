# 笔记落盘（按月）

`notes/` 收的是**面向未知**的东西：问题在手、答案不在，探索比选后收敛出结论。

**REQUIRED BACKGROUND:** 总规则见 `using-docflow`。

## 落盘

```
<落盘根>/notes/<yyyy年MM月>/<NNN-要干什么>.md
```

- **月份**用中文两位格式（`2026年08月`），**归开工那个月**——跨月继续写的不搬家。
- **编号** `NNN` 在月份目录内从 001 递增，一份一号，号不复用；跨月重新从 001 起。
- **命名**：`<要干什么>` 写成一句话点题（`001-高级筛选多选上限怎么定.md`），**别用「方案」「调研」「记录」这类分类词充数**。

## 收什么

1. 方案探讨、技术选型
2. 排查与调研过程
3. 为解决某个具体问题顺手梳理出的机制
4. 已定方案对外交付的规范文档

## 不收什么

- **实现记录** → `changes`（notes 不承担这个职责）
- **系统性归纳「它现在是什么样」** → `analysis`
- **需求分析** → `requirement`

`notes` 与 `analysis` 分不清时：**素材已在手、要归纳成体系 → analysis；问题在手、答案不在 → notes。拿不准先落 notes**，日后真要系统性铺开再开 analysis 主题，notes 那篇留一行指过去。**别两处各写一份。**

## 两条纪律

1. **同一话题后续补充直接改那一篇**，不新开。探讨对象真的换了才新开一篇。
2. **定下来之后**：若要进入开发，正式产物走 `requirement → contract → sql → changes` 那条链路；在 notes 篇末写明指向哪个 `<分支短名>/<NNN-业务>/<NNN-批次>`。

## 建议结构（不强求）

```markdown
# <一句话点题>

> 日期：<yyyy-MM-dd> ｜ 状态：<探讨中 / 已定案 / 已进开发>

## 1. 要解决什么
<问题是什么、为什么现在要解决>

## 2. 现状与约束
<查到的事实。凡涉及数据/代码的，写实际查到的，别凭印象>

## 3. 备选方案
| 方案 | 怎么做 | 优 | 劣 |
|---|---|---|---|

## 4. 结论
<选了哪个、为什么；排除的理由也写下来——防止日后重新纠结一遍>

## 5. 下一步
<若进开发：指向 requirement/<分支短名>/<NNN-业务>/<NNN-批次>；若不进：写明为什么先搁置>
```
