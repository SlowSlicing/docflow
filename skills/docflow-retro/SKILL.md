# 复盘提炼 → 约定库

把散在变更记录、笔记、分析产物里的教训，提炼成**每次开工都会被读到**的项目约定。

这是「越用越聪明」的整理环节：`docflow-changes` 负责随手沉淀单条，本 skill 负责**定期回看、合并、瘦身、淘汰**。

**REQUIRED BACKGROUND:** 约定库位置与条目格式见 `using-docflow`。

## 一条约定长什么样（配方，照此产出）

**一条 = 三部分，按这个顺序，一行写完：**

```
- 【日期】<一句话规则> 出处：<路径>
```

实例：

```markdown
- 【2026-08-23】XORM batchSave 超 500 条会静默截断，批量写入一律分页调用。出处：changes/1.0.0-20260101/001-用户导入/001-初版/002-批量截断改分页.md
- 【2026-08-23】所有写接口都要防重复提交，沿用 requestId + Redis 10 分钟的既有做法。出处：changes/1.0.0-20260101/001-用户导入/001-初版/004-导入接口加幂等键.md
- 【2026-08-23】接收用户上传的文件先探测编码再解析，探测失败回退 UTF-8。出处：changes/1.0.0-20260101/001-用户导入/001-初版/003-导入编码兼容GBK.md
```

**规则那句话最多写到两行。** 需要边界限定就写进这句话里（「仅限用户上传的文件」「读接口不需要」），而不是另起一段。

### 三部分之外的一切，都在出处那条记录里

| 内容 | 归属 |
|---|---|
| 规则本身、适用边界 | **约定库**（就是那一句话） |
| 为什么、怎么发现的、踩坑经过 | 出处记录 |
| 复现步骤、验证方法、代码位置 | 出处记录 |
| 反例、替代方案为什么被排除 | 出处记录 |

**约定库是索引，不是文库。** 它的价值来自「一屏能扫完」——每次开工都要读它，读不完就等于没沉淀。要细节，顺着出处链接回去看。

## 什么值得收

| 信号 | 例子 |
|---|---|
| **带明确禁令的决策** | 「绝不能改回单次全量调用」——反直觉、最容易被后人顺手改坏 |
| **原文自称是通例** | 记录里写「这是团队共识，不是本次特例」——它自己宣告了自己是约定 |
| **成因属于群体属性，不是个例属性** | 「财务同事习惯用旧版 Excel 导出 GBK」→ 只要还是这批人上传，新入口照样踩 → 项目级约定。反之「这个接口的参数比较特殊」→ 只是个例，不收 |
| **被用户当场纠正的做法** | 用户说「别这么写，我们这里一律用 X」 |
| **重复出现第二次的坑** | 同一个坑在两条记录里出现，说明不是偶然 |

## 什么不收

- **只在单个业务成立的细节**——它属于那条变更记录。
- **通用编程常识**——「变量要起有意义的名字」这种，占位置不产生信息。
- **涉及既存事实取舍的**——比如「历史目录撞号要不要修」，这是用户的决定，不是能从记录里推出来的结论。**发现了就问，别自己立规矩。**
- **拿不准的**——列出来问用户，别先写进去。

## 工作流

### 1. 确定复盘范围

读约定库文件头的**复盘水位**（上次复盘覆盖到哪），从那之后新增的记录看起。没有水位记录（首次复盘）就全量扫。

扫描范围：`changes/`（主力）+ `notes/` + `analysis/` 的产物。

### 2. 提炼候选

按上面的「什么值得收」筛。每个候选写成配方三段式，**并标出它来自哪条记录**。

### 3. 与现有条目对照

| 情况 | 处理 |
|---|---|
| 与现有条目**重复** | 不新增；若新记录提供了更好的表述，替换掉旧的（出处链接列出两条） |
| 与现有条目**冲突** | **不擅自决定谁对**——把冲突摆出来问用户，通常意味着口径变了 |
| 是现有条目的**特例** | 考虑并进那条（在规则句里加边界），而不是新开一条 |
| 多条同主题**可以合并** | 提炼成一条更概括的，出处列全 |

### 4. 顺手瘦身

- **超两行的条目**：压缩回一句话，细节退回出处（出处里没有的话，先补进出处记录再压缩）。
- **过时条目**：技术栈换了、口径变了、代码已重构——标注删除并说明理由。
- **条目太多**：单个文件超过一屏（约 40 条）就按域拆到 `001-流程约定.md` / `002-编码约定.md` / `003-踩坑记录.md`。

### 5. 出清单，等确认

**约定库是所有 agent 开工必读的，写错了污染面大。** 所以改动前先列清单：

```markdown
## 建议新增（N 条）
- 【日期】<规则> 出处：<路径>      ← 依据：<为什么值得收>

## 建议合并 / 替换（N 条）
- 把现有第 X 条与第 Y 条合并为：<新表述>

## 建议删除（N 条）
- 第 Z 条 —— 理由：<过时/已失效>

## 需要你定夺
- <冲突项、涉及既存事实取舍的、拿不准的>
```

**等用户确认后才写入。**

### 6. 写入 + 更新水位

确认后落地，并更新约定库文件头的复盘水位：

```markdown
> 最近复盘：2026-08-23，覆盖 changes/ 至 1.0.0-20260101/001-用户导入/001-初版/004。下次从这之后接着看。
```

### 7. 毕业建议（可选）

有些条目稳定到该往上走一层：

- 对**这个项目**长期有效、且比约定更根本的 → 建议提进项目的 `CLAUDE.md` / `AGENTS.md`。
- 对**你所有项目**都成立的（不是这个项目特有的）→ 建议提进个人全局规则，或反馈进 docflow 包本身。

**只给建议，不代劳**——往上层写是用户的决定。

## 自检

- [ ] 每条都是「日期 + 一句话规则（≤2 行）+ 出处链接」三部分？
- [ ] 没有把「为什么」「怎么发现的」搬进约定库？
- [ ] 收的都是能跨业务复用的，没有混进单业务细节？
- [ ] 与现有条目对照过（重复/冲突/特例/可合并）？
- [ ] 冲突项和拿不准的**交给用户定**，没自己拍板？
- [ ] 清单先给用户确认了才写入？
- [ ] 复盘水位更新了？
