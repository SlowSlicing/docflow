# 复盘提炼 → 约定库

把散在变更记录、笔记、分析产物里的教训，提炼成**每次开工都会被读到**的项目约定。

这是「越用越聪明」的整理环节：`docflow-changes` 负责随手沉淀单条，本 skill 负责**回看、合并、瘦身、淘汰**。

**REQUIRED BACKGROUND:** 约定库位置、条目格式、预算与体检命令见 `using-docflow`《约定库》。

两种模式：

| 模式 | 什么时候 | 要不要等确认 |
|---|---|---|
| **自动整理**（只收敛已有条目） | 体检报约定库警告；用户说「约定库太长了」 | **不等**，做完报告。改动可逆：退休的进归档、压掉的细节在出处里 |
| **复盘**（从记录里提炼新约定 ＋ 顺手整理） | 批次收尾、准备发版、用户说「复盘一下」 | 新增条目**出清单等确认**；整理部分同自动整理 |

## 一条约定长什么样（配方，照此产出）

**一条 = 三部分，按这个顺序，一行写完：**

```
- 【日期】<一句话规则> 出处：<引用>　　←「引用」怎么写见 `using-docflow`《引用格式》
```

实例：

```markdown
- 【2026-08-23】XORM batchSave 超 500 条会静默截断，批量写入一律分页调用。出处：002-批量截断改分页.md
- 【2026-08-23】所有写接口都要防重复提交，沿用 requestId + Redis 10 分钟的既有做法。出处：004-导入接口加幂等键.md
- 【2026-08-23】接收用户上传的文件先探测编码再解析，探测失败回退 UTF-8。出处：003-导入编码兼容GBK.md
```

**整条（含日期与出处）不超过单条上限**（默认 150 字，按字符数不按行数）。需要边界限定就写进这句话里（「仅限用户上传的文件」「读接口不需要」），而不是另起一段。

### 三部分之外的一切，都在出处那条记录里

| 内容 | 归属 |
|---|---|
| 规则本身、适用边界 | **约定库**（就是那一句话） |
| 为什么、怎么发现的、踩坑经过 | 出处记录 |
| 复现步骤、验证方法、代码位置 | 出处记录 |
| 反例、替代方案为什么被排除 | 出处记录 |

**约定库是索引，不是文库。** 它的价值来自「一屏能扫完」——每次开工都要读它，读不完就等于没沉淀。要细节，顺着出处链接回去看。

## 什么值得收

| 信号 | 例子 |
|---|---|
| **带明确禁令的决策** | 「绝不能改回单次全量调用」——反直觉、最容易被后人顺手改坏 |
| **原文自称是通例** | 记录里写「这是团队共识，不是本次特例」——它自己宣告了自己是约定 |
| **成因属于群体属性，不是个例属性** | 「财务同事习惯用旧版 Excel 导出 GBK」→ 只要还是这批人上传，新入口照样踩 → 项目级约定。反之「这个接口的参数比较特殊」→ 只是个例，不收 |
| **被用户当场纠正的做法** | 用户说「别这么写，我们这里一律用 X」 |
| **重复出现第二次的坑** | 同一个坑在两条记录里出现，说明不是偶然 |

## 什么不收

- **只在单个业务成立的细节**——它属于那条变更记录。
- **通用编程常识**——「变量要起有意义的名字」这种，占位置不产生信息。
- **涉及既存事实取舍的**——比如「历史目录撞号要不要修」，这是用户的决定，不是能从记录里推出来的结论。**发现了就问，别自己立规矩。**
- **已被卡口挡住或已写进项目 `CLAUDE.md` / `AGENTS.md` 的**——卡口与上层文档才是正本，约定库再抄一份只会先漂。
- **拿不准的**——列出来问用户，别先写进去。

## 自动整理

**目标**：把报警的文件收回到预算的 **80% 以下**（留余量，不然下一条写进来又超）。只动报警的文件。
积压超过预算两倍时按文件分批做，每批做完报告一次。

按顺序做。第 1 步整份文件做完；第 2、3 步每做一批量一次，回到 80% 以下就停：

1. **退休到归档**（**这一步不看预算，整份文件过一遍**——过时条目留着的害处是误导，不是占地方），只认下面几种理由，每条都要**当场核实**：

   | 理由 | 怎么核实 |
   |---|---|
   | 已被卡口挡住 | 能指出是哪个测试、哪条 lint 规则 |
   | 已写进项目 `CLAUDE.md` / `AGENTS.md`（毕业） | 能指出是哪一节 |
   | 过时：引用的文件、符号、命令已不存在 | 对条目里反引号括起来的标识符 grep 代码，**一个都找不到**才算 |
   | 与现状冲突 | 读代码能确定现状是哪一边；判不出来的不动，列进「需要你定夺」 |
   | 只在单个业务成立 | 按上文《什么不收》 |

   退休 = 从原文件删掉，原样追加到 `conventions/归档/<同名文件>` 末尾，后缀写理由：

   ```markdown
   - 【2026-08-23】<原条目原文> 【退休 2026-09-23】已由 tests/test_xxx.py::test_yyy 挡住
   ```
2. **压缩超长条目**：确认细节在出处记录里有（没有就先补进出处记录），再把条目压成一句话规则。
   **边界不许丢**——「仅限 X」「Y 例外」这种限定语是规则的一部分，不是细节。
3. **合并同主题**：说的是同一个组件、同一类坑的，并成一条更概括的，出处列全。
4. **仍然超**：停下，把剩下的条目按「最可能退休」排个序列给用户挑。**不许靠删有效约定硬凑预算**；
   拆出新的域文件只在主题真的分得开时才做，并在报告里说明——拆文件不等于收敛。
   拆的时候文件名写清域（如 `006-测试踩坑.md`），并在原文件头留一行「按域拆出去的：…」，写入方靠它找到该写哪份。

**不许做的**：改规则的意思（合并时丢边界也算）、没核实就判过时、动 `CLAUDE.md` / `AGENTS.md`（往上层写是用户的决定，只能建议）。

**报告**（整理完就发，不等问）：

```markdown
约定库整理：002-编码约定.md 178 条 → 38 条，30000 字 → 6100 字
- 压缩 N 条、合并 N 组（N 条 → N 条）
- 退休 N 条（卡口 N、已进 CLAUDE.md N、过时 N、冲突 N、单业务 N），见 conventions/归档/002-编码约定.md
- 需要你定夺：<判不出现状的冲突、第 4 步剩下的>
- 回看改动：git -C <落盘根>/.. diff
```

## 复盘工作流

### 1. 确定复盘范围

读约定库文件头的**复盘水位**（上次复盘覆盖到哪），从那之后新增的记录看起。没有水位记录（首次复盘）就全量扫。

扫描范围：`changes/`（主力）+ `notes/` + `analysis/` 的产物。

### 2. 提炼候选

按上面的「什么值得收」筛。每个候选写成配方三段式，**并标出它来自哪条记录**。

### 3. 与现有条目对照

| 情况 | 处理 |
|---|---|
| 与现有条目**重复** | 不新增；若新记录提供了更好的表述，替换掉旧的（出处链接列出两条） |
| 与现有条目**冲突** | **不擅自决定谁对**——把冲突摆出来问用户，通常意味着口径变了 |
| 是现有条目的**特例** | 考虑并进那条（在规则句里加边界），而不是新开一条 |
| 多条同主题**可以合并** | 提炼成一条更概括的，出处列全 |

### 4. 顺手瘦身

按上文《自动整理》对整个约定库做一遍（不只报警的文件），结果并进第 5 步的清单一起给出。

### 5. 出清单，等确认

**新增的条目是从记录里推出来的判断，写错了污染所有后续工作**，所以新增部分先列清单（自动整理的部分已经做了，一并报告）：

```markdown
## 建议新增（N 条）
- 【日期】<规则> 出处：<引用>      ← 依据：<为什么值得收>

## 建议合并 / 替换（N 条）
- 把现有第 X 条与第 Y 条合并为：<新表述>

## 建议删除（N 条）
- 第 Z 条 —— 理由：<过时/已失效>

## 需要你定夺
- <冲突项、涉及既存事实取舍的、拿不准的>
```

**等用户确认后才写入。**

### 6. 写入 + 更新水位

确认后落地，并更新约定库文件头的复盘水位：

```markdown
> 最近复盘：2026-08-23，覆盖 changes/ 至 1.0.0-20260101/001-用户导入/001-初版/004。下次从这之后接着看。
```

### 7. 毕业建议（可选）

有些条目稳定到该往上走一层：

- 对**这个项目**长期有效、且比约定更根本的 → 建议提进项目的 `CLAUDE.md` / `AGENTS.md`。
- 对**你所有项目**都成立的（不是这个项目特有的）→ 建议提进个人全局规则，或反馈进 docflow 包本身。

**只给建议，不代劳**——往上层写是用户的决定。

## 自检

- [ ] 每条都是「日期 + 一句话规则 + 出处链接」三部分，整条不超过单条上限？
- [ ] 跑过体检，报警的文件都回到预算 80% 以下了（或剩下的列给用户挑了）？
- [ ] 退休的每条都写了核实过的理由，原文进了归档而不是直接删掉？
- [ ] 没有把「为什么」「怎么发现的」搬进约定库？
- [ ] 收的都是能跨业务复用的，没有混进单业务细节？
- [ ] 与现有条目对照过（重复/冲突/特例/可合并）？
- [ ] 冲突项和拿不准的**交给用户定**，没自己拍板？
- [ ] **新增**条目先给用户确认了才写入？
- [ ] 复盘水位更新了？
