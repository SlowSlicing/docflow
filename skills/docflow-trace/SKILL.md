# 业务历史脉络

回答「这块以前是怎么回事」。输出一份**脉络报告**，不改任何文件。

**REQUIRED BACKGROUND:** 总规则见 `using-docflow`。

## 与 docflow-evolve 的分工

| | 本 skill | docflow-evolve |
|---|---|---|
| 目的 | **只查，出报告** | 查完还要**改**产物 |
| 产出 | 脉络报告（对话里给，不落盘） | 更新后的需求文档/实现计划 |
| 何时用 | 想了解、想排查、想决定要不要动 | 已确定要改 |

`docflow-evolve` 内部也做定位，但它定位完就要出变更说明。**只想知道来龙去脉，用本 skill。**

## 工作流

### 1. 重建索引

```bash
python3 <docflow包>/scripts/build-index.py <落盘根>
```

`INDEX.md` 一行一个业务，含分支短名、批次数、一句话目标、承接自、产物、最近改动——**这是入口，别手工翻目录**。

**没有 python3 / 脚本跑不起来**：按 `using-docflow`《没有 python3 的机器怎么办》用 `ls` + `grep` 扫，脉络报告照出——只是要自己把跨产物类型的信息拼起来。

### 2. 匹配

按关键词在索引里找。注意同一个业务在不同分支可能**换了名字**（「用户导入」→「用户导入优化」→「导入性能治理」），所以：

- 先按关键词匹配业务名；
- 再顺**承接链**（「承接自」字段）往上下游追——这是跨分支追溯最可靠的线索；
- 名字对不上但疑似相关的，读它需求文档的「一句话目标」确认。

匹配不到就换关键词或问用户；**别拿相近的业务凑数**。

### 3. 深读

对确认相关的每个业务·批次，读：

| 读什么 | 取什么 |
|---|---|
| `requirement/…/001-需求文档.md` | 一句话目标、需求澄清里的**口径与非目标**、变更历史表 |
| `requirement/…/001-实现计划.md` | 有没有任务卡在「正在写」（= 可能有半截活） |
| `changes/…/*.md` | **「为什么这么改」**（有意为之的设计）、**「已知遗留」**、复查指引里的易错点 |
| `sql/…/*.sql` | 表结构怎么演变的 |
| `contract/…/*.md` | 契约变过没有、有没有破坏性变更 |

`git -C <落盘仓库> log --oneline -- <路径>` 可补时间线。

### 4. 出报告

在对话里给，**不落盘**（除非用户要求，那属于 `docflow-notes`）：

```markdown
## <业务名> 演进脉络

| 时间 | 分支短名 | 业务 · 批次 | 做了什么 | 关键结论 |
|---|---|---|---|---|
| 2026-01 | 1.0.0-20260101 | 001-用户导入 / 001-初版 | Excel 批量导入 | 单次上限 500，框架限制 |
| 2026-02 | 1.1.0-20260201 | 001-用户导入优化 / 001-初版 | 失败行导出重试 | 承接自 1.0.0 |

### 有意为之的设计（别当 bug 改掉）
- <从 changes 的「为什么这么改」里提取>

### 已知遗留 / 当时没做的
- <从 changes 的「已知遗留」里提取>

### 踩过的坑
- <从复查指引的「易错点」里提取>

### 悬着的活
- <实现计划里状态仍是「正在写」的任务>
```

### 5. 收尾

如果用户接下来要改：提示转 `docflow-evolve`（需求变更）或 `docflow-changes`（直接改代码）。

## 纪律

- **只读不写**：本 skill 除了重建 `INDEX.md`（那是缓存）之外不改任何文件。
- **报告里的每一条都要能指到出处**（哪个文件哪一节），不要凭印象总结。
- **查不到就说查不到**：没有记录的时期就写「无记录」，别脑补演进过程。
