# 需求变更 · 增量更新

已落盘的需求变动了，要在保住历史溯源的前提下增量更新。

**REQUIRED BACKGROUND:** 目录、编号、批次判据见 `using-docflow`；文档模板见 `docflow-requirement/references/templates.md`。

## 🔴 铁律：变更说明先出，用户确认后才动手

**读历史、算差异、想清楚怎么改——这些都可以自己做。但只要是往文件里写，必须先把「打算怎么改」说明白，等用户点头。**

这条最容易失守的方式不是偷懒，恰恰是「分析得很认真，然后顺手就把活干完了」：

| 表现 | 为什么不行 |
|---|---|
| 读全了演进链，想清楚了该开新业务目录，直接建了，事后说「你要是想改老的，说一声我改」 | 「改哪份文档」是结构决策，改完再问等于让用户做撤销决策。而且新建的业务目录会占号、进索引、被别人读到 |
| 定位到两处历史，自己挑了一处承接就开始写 | 挑哪处是用户的判断（他知道哪条线是活的），不是你的 |
| 「用户说『帮我改一下需求文档』，这就是授权了」 | 授权的是「改」这件事，不是「怎么改」。续写还是开新批、改哪一份、占哪个号，都还没定 |
| 同一次对话里连着处理两个变更，各自建了业务目录 | 没先汇总确认，两次各取最小可用号 → **撞号**。这是真实发生过的后果 |

**动笔前的最后一问：我把「改哪个文件、增删改哪些要点、续写还是开新批次、影响面」四项说清楚了吗？用户点头了吗？**

## 工作流

### 1. 开工三读 + 重建索引

先做 `using-docflow` 的开工三读，然后重建索引：

```bash
python3 <docflow包>/scripts/build-index.py <落盘根>
```

读 `<落盘根>/INDEX.md`——它一行一个业务，带分支短名、批次数、一句话目标、承接链，是定位历史最快的入口。**别手工翻目录。**

**没有 python3 / 脚本跑不起来**：按 `using-docflow`《没有 python3 的机器怎么办》改用 `ls` + `grep` 扫目录，**照常往下走**——索引只是加速器，定位历史不依赖它。只是要自己留意撞号（定新编号前 `ls` 确认没被占）。

### 2. 定位历史产物

按业务关键词在索引里匹配：

| 命中情况 | 怎么办 |
|---|---|
| **命中一处** | 读那份需求文档确认确实是它，再往下走 |
| **命中多处**（跨分支 / 多批次 / 名字相近） | **列脉络让用户选**：每处给出「分支短名 · 业务 · 最新批次 · 一句话目标 · 最近改动 · 承接关系」，按承接链排序，问用户「这次承接哪一处？要在当前分支开新业务目录，还是在原处开新批次？」**绝不自己挑一个** |
| **命中 0** | 可能是全新需求 → 提示用户转 `docflow-requirement`；也可能是关键词不对 → 换词再找或问用户 |

### 3. 读全变动内容 + 读全现有需求

- 把「变动内容」也当原始需求**逐条读全、拆成变动要点清单**（全覆盖铁律同样适用于增量，别漏一条）。
- 通读被定位到的现有需求文档 + 它的要点清单。
- **逐条比对算 delta**：哪些要点新增、哪些修改（改成什么）、哪些删除。

### 4. 消歧

变动里不明确、两可的照旧问用户，清零为止。这一步没做完不要进第 5 步——**变更说明里不该有「暂定」。**

### 5. 出变更说明（硬门槛，等确认）

清楚列出四项，**等用户确认或调整后才动手**：

1. **改哪个文件**：`001-需求文档.md` / `001-实现计划.md`（可能多份、多业务），写全路径。
2. **增删改哪些要点**：逐条对到现有要点清单的编号——新增第几条、把第几条改成什么、删第几条。
3. **续写当前批次，还是开新批次**（本步最关键，判据见 `using-docflow`《什么时候开新批次》）：
   - 开新批次 → 说明新批次目录名 `<NNN+1>-<本批做的事>`，**并确认这个号没被占**（索引里核对）。
   - 续写 → 说明在哪个批次的哪份文件里原地改。
4. **影响面**：受影响的实现计划任务；**是否动了接口契约**（动了且配置启用 contract → 要出对接方案）；下游 changes / sql 是否需要重新对齐。

### 6. 确认后落地

**开新批次时，上一批次的产物保持原样不动**——它们是已经发生的历史。被推翻的部分在新批次里写明，新需求文档的「承接自」指向上一批次目录。

- **更新「1. 原始需求」**：保留原始内容不删，**追加**本次变动的来源途径 + 日期 + 变动原文。
- **「变更历史」表追加一行**：日期、变动来源、变动摘要（对到要点编号）、落到哪里。
- **更新要点清单及其去向**，让新/改/删的要点都可核对。
- **同步实现计划**：新增/调整任务；已完成又被推翻的任务要显式改回并说明。
- **落盘门槛照旧**：变动要点 100% 覆盖 + 零模糊才算改完。

### 7. 收尾

告知改了哪些文件 + 一句话变更摘要；下游产物（changes / contract / sql）受影响的话提示用户按各自规则同步。

## 红线自检

- [ ] 重建索引后定位的，不是手工翻目录猜的？
- [ ] 命中多处时**列了脉络让用户选**，没有自己挑一个？
- [ ] **变更说明四项都写了，并且拿到用户确认才动的手**？
- [ ] 开新批次时上一批产物一个字没动，新文档写了「承接自」？
- [ ] 原始需求的原始内容没被删，只做了追加？
- [ ] 变更历史表追加了一行？
- [ ] 新占的编号在索引里核对过，没撞号？
- [ ] 变动要点逐条有去向，没漏？
