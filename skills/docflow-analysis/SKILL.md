# 分析模式

把「分析 → 总结 → 归纳 → 答疑复用」做成一条可落盘、可跨终端续接的工作流。核心闭环：

**原始素材 → 分析 → 总结 → 归纳（规范文档）→ 答疑复用 →（有新问题）再分析 → 再归纳。**

所有产物写进「一个主题目录 + 阶段子目录」，结构清晰，换终端后能续接。

## 触发方式

- **`进入分析模式`**（无参数）→ 开启**新**分析主题。
- **`继续分析 <目录路径>`** → 读取该目录，**续接**已有主题。

进入后，用户抛出内容/问题/要求，按下面的动作响应（由用户意图决定用哪个）。

## 落盘位置

**优先读项目配置**：若项目已接入 docflow（存在 `<落盘根>/000-项目配置.md`），主题目录放

```
<落盘根>/analysis/<yyyy年MM月>/<NNN-主题>/
```

月份用中文两位格式，归开工那个月；`NNN` 在月份目录内从 001 递增。**此时不必再问用户放哪。**

没有项目配置时，才按下面《何时询问存储目录》问一次。

## 目录结构（每个分析主题一个目录）

```
<主题目录>/
  README.md              # 概览 + 当前进展 + 未决问题 + 文件索引 + 权威文档指针
  inputs/                # 原始问题、素材、要求
    001-<简述>.md
  analysis/              # 分析过程与结论（多篇，序号累加）
  summary/               # 总结（多篇）
  topics/                # 专题文档（面向交付的独立成品单篇）
  归纳.md                # ★ 权威规范文档：归纳动作产出，可反复重建；答疑的唯一参考源
```

- 文件命名 `序号-简述.md`，序号三位、主题内累加。
- `归纳.md` 用单一根文件；内容过大再拆 `knowledge/` 目录。
- `topics/` 只在用户要「单独出一篇文档」时才创建，**平时不建空目录**。

## 五个动作

| 动作 | 输入 | 产出 | 落盘位置 |
|---|---|---|---|
| **分析** | 用户给的内容 + 要求（先存入 `inputs/`） | 分析过程与结论 | `analysis/NNN-简述.md` |
| **总结** | 已有分析 | 针对某段分析的阶段性归纳 | `summary/NNN-简述.md` |
| **专题文档** | 用户要「单独出一篇文档」 | 自包含、可独立阅读的**交付成品单篇** | `topics/NNN-简述.md` |
| **归纳** | `inputs/ + analysis/ + summary/` 全部内容 | 规范、自洽、可独立阅读的权威文档 | `归纳.md`（**重建式覆盖**） |
| **答疑** | 用户的新问题 | 直接回答 | 不落盘（除非用户要求） |

每次「分析 / 总结 / 专题文档 / 归纳」落盘后，**必须回写 `README.md`**（更新进展、未决问题、文件索引）。

**三者别混**：

- **分析**是过程记录：碎、按阶段累加，服务于后续归纳，不追求单篇自洽。
- **专题文档**是面向交付的成品单篇：自包含、可脱离其他文件独立阅读，聚焦某子主题深入展开。各专题相互独立、各自增删，**不被归纳覆盖**。
- **归纳**是全主题唯一权威源：**重建式覆盖** `归纳.md`，是答疑的首选参考。

触发词判断：出现「单独 / 独立 / 单独出一篇 / 生成一个文档 / 导出 / 成一篇」→ 走**专题文档**；出现「归纳 / 汇总成权威文档 / 整理成规范」→ 走**归纳**。拿不准就问用户：「放进 `归纳.md`（权威源，会覆盖重建）还是单独出一篇 `topics/` 专题文档？」

## 出处纪律（硬性要求）

`analysis/`、`summary/`、`topics/`、`归纳.md` 中的**每个关键结论必须标注出处**：

| 素材类型 | 出处格式 | 示例 |
|---|---|---|
| 代码 | `仓库相对路径:行号`（宜附 `类名#方法名`） | `service/impl/FooServiceImpl.java:123`（`FooServiceImpl#doSync`） |
| 本地文档/素材 | `文件路径 § 章节` | `inputs/001-需求原文.md § 三、对账规则` |
| 网页 | URL（必要时带锚点） | `https://example.com/pricing § 企业版` |
| 本主题已有产物 | 主题内相对路径 | `analysis/002-竞品定价.md` |

- **无出处的推断必须显式标「推断」**，不得与有据结论混写。
- **归纳时出处随结论一起带入**——重建式覆盖不是丢出处的借口。
- 答疑引用 `归纳.md` 后被追问依据时，按文档内出处回溯原素材，而不是现场重新推断。

**归纳是重建式的**：每次归纳基于当前全部内容重新生成 `归纳.md` 以保证自洽，不是往旧文档尾部追加。

**答疑优先查归纳文档**：主题下一旦存在 `归纳.md`，用户再提问时先读它；未覆盖就**明说「归纳文档里没有」**，再走分析流程补充。

## 何时询问存储目录

只有**新主题 + 项目未接入 docflow** 时才问，且**等到第一次真要落盘才问一次**（别一进入就打断用户表达）。

- **续接**（`继续分析 <路径>`）：路径已给，**绝不再问**。
- **项目已接入 docflow**：按配置落，**不问**。
- 总结、归纳、答疑：都不问。

## 续接流程（换新终端后）

1. 用户：`继续分析 <路径>`
2. 读 `README.md`，再扫 `inputs/ analysis/ summary/ 归纳.md` 重建上下文。
3. 简要复述「当前进展 + 未决问题」，然后继续听指令。

## README.md 模板

```markdown
# <主题名>

## 概览
一句话说明这个分析主题在研究什么。

## 当前进展
- 已完成：...
- 进行中：...

## 未决问题
- [ ] ...

## 文件索引
- inputs/001-xxx.md — ...
- analysis/001-xxx.md — ...
- summary/001-xxx.md — ...
- topics/001-xxx.md — ...（如有）

## 权威文档
- 归纳.md（是否已生成 / 最近更新覆盖了哪些内容）
```

## 与 docflow-notes 的分界

| | docflow-analysis | docflow-notes |
|---|---|---|
| 起点 | 素材已在手（代码、库表、文档） | 问题在手，答案不在 |
| 过程 | 通读 → 归纳 → 成规范文档，跨终端多阶段续接 | 探索、比选、试错，收敛出结论 |
| 产出 | 「它现在是什么样」 | 「到底怎么回事 / 我们决定怎么做」 |
| 形态 | 主题目录 + 阶段子目录 | 单篇 md |

**分不清先落 notes**，日后真要系统性铺开再开 analysis 主题，notes 那篇留一行指过去。**别两处各写一份。**

## 常见错误

- **续接时又问目录**：路径已给，直接读。
- **项目已接入 docflow 还问目录**：按配置落即可。
- **归纳变成追加**：必须基于全部内容重建 `归纳.md`。
- **答疑不查归纳文档**：有就先查它。
- **落盘后忘更新 README**：每次写文件都要回写进展与索引，否则续接会断档。
- **把所有内容塞进一个文件**：分析/总结/归纳分目录分文件。
- **结论不带出处**：按《出处纪律》标，纯推断显式标「推断」。
- **新分析太早问目录**：等真要落盘再问。
