# 变更记录

讲清楚这次动了什么、各层怎么对应。这份记录有两个读者：**几个月后的你**（追溯为什么这么改），和**出 bug 时来排查的 agent**（拿它当第一手定位依据）。按后者的标准写——该留的定位信息留全。

**REQUIRED BACKGROUND:** 目录与编号规则、约定库条目格式见 `using-docflow`。模板见 `references/templates.md`。

## 两条原则

1. **改完之后回填，不是边写边猜**——记录要反映最终真实实现。
   **「改完」指代码写完，不是「用户验证通过」。** 验证是记录之后的事：挂在「等你自测通过我再写」上，改动就会在没有档案的状态下过夜，而这段时间恰恰最容易被中断。验证真发现问题 → 照常改，再落一条标「修正 NNN」（见下方《落盘》）。落点同理是**报备不是选择题**：直接写，写完把路径告诉用户。
2. **按本次实际涉及的层如实记，没涉及的不硬凑**——这次没动表就不编表操作，没改接口就不列接口字段。查不到的（比如代码不在手边）显式标「待回填」，**不要编造**。

## 「改动小，这次就不记了吧」——不成立

记录**粒度**可以小（一行改动写十几行记录足够），但**跳过**不行。

一行判空恰恰是价值最高的那类：几个月后它最容易被当成冗余代码删掉、或被复查的 agent 当 bug「改回去」。模板里「为什么这么改」那节防的就是这个。

## 落盘

```
<落盘根>/changes/<分支短名>/<NNN-业务>/<NNN-批次>/<NNN-简述>.md
```

- **每次修改新增一条**，编号在该批次目录内从 001 递增。时间线集中，好翻。
- 批次归属：自测 bug、把没写完的写完、评审重构 → **归当前批次**；产品改了需求 → 那是 `docflow-evolve` 的事，先去开新批次。
- 若本条**修正/取代**了同批次此前某条记录，显式标注「取代 / 修正 NNN」——否则日后复查的 agent 会拿到过时那条被带偏。

## 必含七项

| # | 内容 | 要点 |
|---|---|---|
| 1 | **变更元信息** | 编号 / 日期 / 关联需求或分支 / 一句话摘要 /（若有）取代哪条 |
| 2 | **层次对照表** ⭐ | 按配置「变更记录层次映射」生成表头，把各层在**同一行对齐**，逐行标 CRUD（接口层：增/删/改/查；存储层：读/写/DDL）。这是核心，务必让每个字段都能一眼连到落地位置 |
| 3 | **影响面 / 兼容性** | 关联的其他接口/页面、是否破坏兼容、是否需要迁移或 DDL。**含 DDL / 数据迁移 / 配置变更时必须补「回滚方式」**——这类改动回滚不对称，不能简单 revert |
| 4 | **关联产物** | 对应的 requirement / contract / sql 路径（同业务同批次下同号对齐） |
| 5 | **契约必答问** | *（仅配置启用 contract 时问）* 本次动接口契约了吗（新增/删除接口、改字段、改枚举、改口径）？动了就必须有对应的对接方案，写清路径 |
| 6 | **为什么这么改** | 关键取舍：为什么选这个方案、排除了哪些做法、**哪些是有意为之**。防止日后 agent 把刻意的设计当 bug 改回去 |
| 7 | **已知遗留 / 未覆盖** | 本次**有意**没做的边界、临时方案、待优化点。与「易错点」区分：易错点是容易出错的地方，这里是明知没做的口子 |

### 复查指引块（本次涉及才写）

把关键定位信息集中列出，让日后排查的 agent 拿这一块就能直接定位：

- **改了哪些关键文件·类·方法**（带仓库相对路径，标出核心改动点在哪几处）
- **涉及的关键查询 / 库表**（动了或依赖了哪些语句、哪些表的哪些字段，有 DDL/迁移则点明）
- **易错点 · 风险点 · 边界假设**（依赖的前提、坑点、共享符号的影响面、容易回归出错的地方）
- **怎么验证这次改动是对的**（验证入口、构造什么数据、预期结果）

## 🔴 顺手一问：沉淀进约定库

**写完记录后，固定问自己一句：**

> 这次有没有「被用户纠正的做法」「新定的口径」「踩到的坑」？

有 → 按下面三步写进 `<落盘根>/conventions/`（流程类进 `001-流程约定.md`，编码类进 `002-编码约定.md`，坑进 `003-踩坑记录.md`；**项目按域另拆过文件的，先 `ls` 一下，写进最贴的那一份**）。**没有就不写，不硬凑。**

**为什么这一步不能省**：变更记录是「这一次改动」的档案，只有回头查那条记录的人才会读到。而下次别的 agent 在别的业务里踩同一个坑时，不会去翻那份记录——**约定库是开工必读的，变更记录不是**。不沉淀，坑就会重踩，「越用越聪明」的闭环断在这里。

### 先查、再写、写完量一下

1. **先查有没有同主题的**：在约定库里 grep 这次的关键词（涉及的组件、命令、表、报错）。
   - 已有同主题的 → **改那一条**（补边界、换更准的表述、出处追加本条记录），不新增。
   - 与已有条目口径相反 → 以现状为准改掉旧的；**现状判不出来就问用户**，别两条并存。
   - 这条教训已经被测试、lint 或项目 `CLAUDE.md` / `AGENTS.md` 挡住或写明了 → **不收**。卡口本身就是约定，抄一份只会先漂。
2. **再写**：日期 + 一句话规则 + 出处，整条不超过单条上限（默认 150 字）。写不进就是把细节搬进来了，删到只剩规则。
   出处怎么写见 `using-docflow`《引用格式》——**带描述的文件名全局唯一，只写文件名即可**。

   ```markdown
   - 【2026-08-23】X 框架批量接口超 500 条会静默截断，批量调用一律分页。出处：002-批量截断改分页.md
   ```
3. **写完跑一次体检**（`using-docflow`《预算》那条命令）。有约定库警告 → **当场按 `docflow-retro`《自动整理》把报警的文件收回预算内**，不等用户开口；整理结果一并写进本次汇报。

## sql 产物（配置启用 sql 时）

同批次目录下**只保留一个** sql 文件，前缀固定 `001-`（如 `001-migrate.sql`），后续**直接更新这一个文件**不新增；辅助脚本从 `002` 起。

## 红线自检

- [ ] 记录是**代码写完当场**回填的，反映真实实现——不是边写边猜，也没挂在「等用户验证通过」后面？
- [ ] 层次对照表每行都标了 CRUD，字段能连到落地位置？
- [ ] 查不到的部分标了「待回填」，没有编造？
- [ ] 有 DDL / 迁移 / 配置变更的话，写了回滚方式？
- [ ] 契约必答问答了（配置启用 contract 时）？
- [ ] 「为什么这么改」写了有意为之的部分，防止日后被当 bug 改回去？
- [ ] **顺手一问做了**——有教训/新口径就沉淀进约定库了：先查过同主题、整条不超上限、写完跑过体检，超预算的当场整理了？
- [ ] 编号在批次目录内递增，没覆盖已有记录？
