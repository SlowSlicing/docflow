# 需求分析落盘

把产品的原始需求转成规范产物：按需拆成一或多个业务，每个业务产出**需求文档 + 实现计划**（成对同号），并保真记录原始需求来源。

这是开发全链路的最上游。**本 skill 只做到 requirement 就停**，不写代码、不生成下游产物。

**REQUIRED BACKGROUND:** 目录与编号规则见 `using-docflow`。模板见 `references/templates.md`。

## 🔴 铁律 0：落盘是终点，不是过程动作

**生成需求文档是本轮工作的最后一步，不是第一步。**

前面无论做多少轮，都只是在「分析 → 确认 → 消除模糊」。只有当所有两可、待定、看情况**全部清零**，需求结合项目现状已经完全明确，才落盘。**任何一处还悬着，就继续澄清。**

### 这条最容易被绕过，以下自辩全部无效

| 自辩 | 为什么不成立 |
|---|---|
| 「用户说赶时间/直接落盘，这是显式指令」 | 用户要的是「快点把需求搞清楚落下来」，不是「快点产出一个不能开发的文件」。带着 7 个待确认项的文档，开发时还得回来重问一遍，反而更慢 |
| 「我落的是标注了『待确认』的诚实草稿，不算冒充完成品」 | **这正是要堵的口子。** 标注待确认不等于可以落盘——问题该现在问，不是写进文件里等人回来看 |
| 「单轮对话没法往返澄清，只能先落」 | 那就**不落**，把问题列出来交回给用户。少一个文件不会有任何损失，多一个半成品文件会被当成已完成的需求去开发 |
| 「先落个骨架占位，后面补」 | 占位文件会进索引、会被别人读到、会撞号。要么明确要么不落 |
| 「口径我都标了『暂定』，实现前会再确认」 | 暂定口径会被当成结论执行。真有必须暂定的，说明澄清还没做完 |

**唯一的例外**：原始需求正文取不到（文档需登录、附件没拿到）时，可以留一处占位并向用户索取——这是**来源缺失**，不是口径不明。

## 铁律 1-6

| # | 铁律 |
|---|---|
| 1 | **只到 requirement 停**：只产出需求文档 + 实现计划（+ 按需 README），不生成 contract/sql/changes、不写代码，落盘后把控制权交回用户 |
| 2 | **来源保真 · 全量覆盖**：原始需求逐字逐条读全，拆成逐条要点清单，每条都要有去向。漏一条可能让最终结果不可用 |
| 3 | **拆分先确认**：需求偏大要拆多业务时，先给出拆分方案（几个业务、各自编号+名字+边界）让用户确认 |
| 4 | **不猜，先问**：口径选择、边界、非目标有不确定就问用户，别拿猜的写进「已确认」 |
| 5 | **查真实情况**：现状调查按配置「现状调查数据源」查真实表/接口，不凭实体类或想象。配置为「无」时，现状以代码阅读为准并注明 |
| 6 | **目录守规则**：按 `using-docflow` 放；与其他产物类型同业务同批次**同号同名** |

## 工作流

先判断走哪条：现有 requirement 里**没有**对应业务 → 本 skill；已落盘需求**变动** → 转 `docflow-evolve`。

### 1. 采集原始需求 + 来源

| 来源形态 | 处理 |
|---|---|
| 一段需求描述文字 | 照抄原文进「原始内容」；来源途径写「需求描述文字」+ 提出人/日期 |
| 文档地址（PRD/在线文档/网页/本地文件） | **能读就读**（本地用 Read、可公开访问的 URL 用 WebFetch），取到正文存快照；读不到就把地址原样记档，**让用户把正文贴进来**。无论能否读取，地址都完整记进「来源途径」 |

拿到正文后**先通读全文再拆条**：

- **读全**：逐字读完整份，别只扫标题摘要。附件、表格、截图里的字、评论批注里的补充要求，都算原始需求。
- **拆成逐条要点清单**：拆成一条条离散要点（功能点、规则、字段、边界、约束、例子、异常路径），编号列出。**这份清单是后面「全量覆盖」核对的底账。**
- **拆得到但读不到的部分**（「详见附件 X」但附件没拿到）→ 明确列为缺口向用户索取，不要跳过当没有。

### 2. 确定分支短名

按配置「分支短名规则」取，`git branch --show-current` 确认。

### 3. 拆分决策（先确认）

用下方启发式判断一个业务还是多个，给出建议拆分（业务名 + 拟编号 + 各自边界）让用户确认后再继续。

### 4. 定编号与目录

进 `<落盘根>/requirement/<分支短名>/` 看已有业务：

- **业务层**：复用已存在的、或新建 `NNN-<业务简述>`（现有最大号 +1；多业务连续分配）。
- **批次层**：新业务 → `001-初版`。已有业务且这次是新需求/改需求 → 新建批次；只是补明确 → 续用当前最大号批次。
- **拿不准是续写还是开新批 → 问用户。**

### 5. 需求澄清

把边界、口径选择、非目标与用户逐条确认，**确认结论才写进「需求澄清」**。

对话纪律：一次只问一个问题；能给选择题就给选择题（附上你的推荐）；方案分析处先给 2-3 个方案带推荐再定；YAGNI 砍掉不必要的。

### 6. 现状调查

按配置查真实表结构 / 现有接口 / 对端契约，写「现状与方案分析」「影响面预判」。requirement 阶段做到影响面预判深度即可，不必写到最终 SQL/代码。

### 7. 落盘门槛（硬门槛）

逐项过关，**任一项没过就回到第 3-6 步继续澄清，不落盘**：

- [ ] **要点清单 100% 覆盖**：逐条核对，每条都能指到「落在哪个业务/需求文档的哪部分」或明确标为非目标/已排除——**一条都不能悬空**
- [ ] 所有边界、口径、非目标**已与用户确认**，没有「待定/两可/看情况/暂定」
- [ ] 每个字段/枚举/取值都能**对到项目里的真实表或接口**，不是悬空概念
- [ ] 拆分方案已确认，每个业务都能独立成一份明确的实现计划
- [ ] 没有 TBD / 待补（来源正文取不到那处占位除外）

全过了 → 在 `<落盘根>/requirement/<分支短名>/<NNN-业务>/<NNN-批次>/` 落：

- `001-需求文档.md`（含来源与要点清单）
- `001-实现计划.md`（任务清单，初始状态全「未开始」）
- 衍生文档从 `002` 起（盘点、清单、验收方案……按产出先后递增）

### 8. 落盘后自查

用新眼睛过四问，就地修：① **占位符**——有没有 TBD/空段？② **自相矛盾**——澄清结论与方案/影响面打架没？③ **范围**——是否聚焦到「一个业务对应一份实现计划」？④ **歧义**——有没有能两种理解的表述？有就挑一种写明确。

**发现仍有模糊 → 退回澄清，别靠改文字硬圆。**

### 9. 收尾

告知所有落盘路径，**停在此处**，把控制权交回用户。

## 拆分判定启发式

**倾向拆成多个业务**：命中多个不相关的功能模块或跨业务域；各部分可独立开发、独立联调、独立上线；各自影响面基本不重叠。

**倾向合并为一个业务**：同一功能点的一组紧耦合改动；拆开后彼此强依赖、无法单独交付。

拿不准就把两种切法都摆出来让用户定。

## 红线自检

- [ ] **落盘门槛过了**——模糊全部清零，不是靠「标注待确认」蒙混过关？
- [ ] 原始需求通读了全文（含附件/表格/批注），要点清单每条都有去向，没漏没丢？
- [ ] 「来源途径」写清了（原文照抄 / 地址原样保留），尽量存了正文快照？
- [ ] 需求偏大时，拆分方案先让用户确认过了？
- [ ] 「已确认」里每条都是真跟用户确认过的，没有拿猜的充数？
- [ ] 现状是查的真实表 + 真实代码？
- [ ] 分支短名、编号、业务名与其他产物类型对齐，没往上层扁平堆？
- [ ] 只产出了 requirement，没顺手生成 sql/changes/contract 或写代码？
- [ ] 实现计划任务初始状态全「未开始」，粒度到「一个任务对应一段可写的代码」？
