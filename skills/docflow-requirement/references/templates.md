# 需求分析产物模板

三份：**需求文档**（必出）、**实现计划**（必出，与需求文档成对同号）、**README**（按需）。

落盘路径：`<落盘根>/requirement/<分支短名>/<NNN-业务简述>/<NNN-批次>/`

> 批次内的文件号是一条流水号：主文档（需求文档 + 实现计划）**固定成对占 `001`**；衍生文档（盘点/清单/审计/验收方案/待确认问题…）从 `002` 起按产出先后递增。

---

## 1. 需求文档 —— `001-需求文档.md`

文件名**固定叫「需求文档」**，不另起别名。

> ⚠️ 开头的四行元信息**格式固定、一行都不能少**——索引脚本 `build-index.py` 靠它们抓取「一句话目标」与「承接自」。改了格式索引就读不到。

```markdown
# <NNN> <业务简述> · 需求文档

- 编号：<NNN>
- 分支：<完整分支名，如 feature/x/1.2.0-20260301>
- 一句话目标：<一句话说清这个业务要做成什么>
- 承接自：<相对落盘根的上游批次目录路径，如 requirement/1.0.0-20260101/001-用户导入/001-初版；全新业务写「无」>

## 1. 原始需求（含来源）

- **来源途径**：<必填，据实记录，能多写就多写>
  - 需求描述文字：<若来源是口头/文字描述，把原文照抄进来>
  - 原始需求文档地址：<PRD / 在线文档 / 网页 URL / 本地文件绝对路径，原样保留可点击>
  - 提出人 / 日期 / 关联工单：<有就写>
- **原始内容**：<产品原始需求正文照抄或粘贴；读不到正文时写「（正文见上方地址，未取到，待补）」并向用户索取>

### 需求要点清单（逐条 · 全覆盖核对）

把原始需求拆成逐条离散要点，编号列全（功能点/规则/字段/边界/约束/例子/异常路径……）；每条标注**去向**，用于落盘门槛的 100% 覆盖核对，**不许有条目悬空**。

| # | 原始需求要点（照原意，别加工） | 去向 |
|---|---|---|
| 1 | <要点> | 本业务 · <需求文档第 N 节> / 拆到 `<NNN2>-<业务>` / 非目标 / 已排除（原因） |
| 2 | … | … |

## 2. 需求澄清（已与需求方确认）

- <逐条列出确认过的问答、边界、口径选择（选了哪个方案、哪种匹配策略等）>
- **非目标**：<明确「不做什么」，越具体越好>

## 3. 现状与方案分析

- <涉及的现有接口/表/逻辑现状——引用真实查到的表结构字段、现有接口结构，别凭实体类想象>
- <备选方案对比与选型理由>

## 4. 影响面预判

- <预计要动的模块/接口/表；是否需要 DDL 或数据迁移>
- <对其他接口 / 页面 / 业务的影响；是否破坏兼容>

## 变更历史（需求变动时追加，由 docflow-evolve 维护）

| 日期 | 变动来源途径 | 变动摘要（对到要点清单编号：新增/改/删） | 落到 |
|---|---|---|---|
| <yyyy-MM-dd> | <这次变动的来源：口述/文档地址/工单> | <如：改第 3 条口径为 X；新增第 9 条 Y；删第 5 条> | 原地更新本文件 / 已开新批次 `<NNN>-<批次>` |

## 关联产物

- 实现计划：`001-实现计划.md`
- 对接方案：`<落盘根>/contract/<分支短名>/<NNN-业务>/<NNN-批次>/001-接口开发方案.md`（配置启用 contract 且动了接口契约才有）
- 变更记录：`<落盘根>/changes/<分支短名>/<NNN-业务>/<NNN-批次>/`（开发时产出）
- SQL：`<落盘根>/sql/<分支短名>/<NNN-业务>/<NNN-批次>/`（配置启用 sql 且有 DDL/迁移时产出）
```

**字段要点**

- **来源途径是整条链路的溯源锚点**，必填。文字描述照抄原文，文档地址原样保留，两者兼有就都写。
- **要点清单是反遗漏底账**：逐条拆全、每条标去向，落盘门槛拿它核对 100% 覆盖。要点按原意抄，不要提前加工、合并、丢细节。
- **原始内容尽量存正文快照**，避免日后源文档被改/删后追不回。
- **「承接自」不能瞎填**：写了就必须是真实存在的路径（索引脚本会报悬空引用）。

## 2. 实现计划 —— `001-实现计划.md`

文件名**固定叫「实现计划」**。把需求拆成一份可执行、**可动态更新状态**的任务清单。

```markdown
# <NNN> <业务简述> · 实现计划

任务状态：未开始 / 正在写 / 已完成

- [未开始] 1. <任务，动词开头，落到具体文件/层：如「XxxDTO 新增字段 yyy」>
- [未开始] 2. <多步编排用「流程：…」概括，粒度到「一个任务对应一段可写的代码」>
- [未开始] 3. <验证类任务：查库确认 xxx 语义 / 核对表约束>
- [未开始] 4. <接口契约变化时：产出对接方案到 contract/…/001-接口开发方案.md>
- [未开始] 5. <产出变更记录（层次对照）>

## 备注
- <非目标、共用方法、自动生效点等提示>
```

**状态维护铁律**（开发阶段执行，写在计划里提醒）

- 只用三种状态：**未开始 / 正在写 / 已完成**。
- 动某任务前先置「正在写」→ 写完立即置「已完成」。**一个任务一改，别攒着批量更新**——中断时才不会丢进度。
- 中断恢复时，先对所有「正在写」的任务**对照真实代码复验**改到哪了，再决定续写或回退。
- requirement 阶段只负责把清单列全、初始状态一律「未开始」；推进状态是开发阶段的事。

**仅当**该业务参考了项目内已有的开发文档才建。放在**业务层**（不进批次层），作为该业务跨批次的说明入口。

```markdown
# <NNN> <业务简述> · 说明入口

## 关联产物
- 需求：各批次下的 `001-需求文档.md` / `001-实现计划.md`

- SQL：`<落盘根>/sql/<分支短名>/<NNN-业务>/`
```
